## 적용 조건

**상시 적용한다** — auto mode·연속 실행 중이든, 정당하게 멈춰 사용자에게 물어야 하는 순간이든 예외 없다. 팝업 금지는 "흐름을 끊지 않기 위해서"만이 아니라 **사용자가 그 팝업 UI 자체를 어떤 순간에도 원하지 않기 때문**이다 — 그래서 흐름이 멈추는 정지 시점에도 그대로 유효하다.

## ★ 정지(when)와 팝업(how)은 별개 축이다 — 혼동 금지

**멈추는 것(정지)과 팝업으로 묻는 것(수단)은 완전히 다른 문제다.**

- **멈추는 것은 허용된다** — 사용자만 결정할 수 있는 blocking 사안(헌법 정지 조건)에서 멈추는 것은 의도된 정상 동작이다. 파괴·비가역은 계획 §11 「멈출 일 미리 점검」에 있거나 복원 지점(git 커밋·사본)을 만들 수 있으면 멈추지 않고 **복원 지점 먼저 → 진행 → 기록**이고, §11 에 없고 복원 지점도 만들 수 없을 때만 멈춘다(아래 판정).
- **그러나 그때 묻는 수단은 언제나 본문 평문(prose)이다** — AskUserQuestion·확인 모달·선택지 창을 **띄우지 않는다.** "지금은 어차피 멈추는 상황이니(흐름 유지 관심사 밖) 팝업으로 물어도 된다"는 **틀린 추론**이다. 정지 시점에도 팝업은 금지다.
- 즉 **"정지 = OK, 팝업 = 어떤 순간에도 X."** 결정이 필요해 멈출 때마다 팝업을 띄우는 것이 바로 이 지침이 막으려는 행동이다.
- **사용자의 추가 지시는 정지가 아니다(원본).** 「사용자 stop」(정지 조건)은 사용자가 **명시적으로 중단하라고 한 경우뿐**이다. 작업 중 받은 사용자의 추가 지시는 진행 중 작업을 수정·정정하거나 병행 검토하라는 지시이므로, 멈추지 않고 그 지시를 반영해 고치거나 병행 검토로 돌리고 작업은 이어 간다 — 질문·의견 요청이 섞여 있어도 답하면서 작업은 계속한다. **그 메시지에는 같은 턴 안에서 답한다**(컴팩션 직후면 규칙 파일 재독 다음 — [[feedback_compaction_recovery]] · 턴 도중 도착한 메시지는 그 턴에서 답하고 세션 기록 대기열 대조는 스텝 끝·컴팩션 뒤 — 절차 = `skill:skill_LKS_original_multi-session-orchestration` 「운용 파라미터」) — 그 턴에서 하던 일(발주·편집·기록)을 잇고, 답은 그 턴의 마지막 글로 낸다(도구 호출 사이에 낸 글은 화면에 남지 않는다 — 원본 = [[feedback_communication_style]] 원칙 6 · 답에 사실 확인이 필요하면 그 확인 읽기를 그 턴 안에서 한다 — 예: 이미 정한 모델·설정·결정은 요청 대장부터). 요청 대장 기록은 그 턴 안에서 다음 발주 전이다(적는 시점 원본 = `skill:skill_LKS_original_plan-execution` 2c-2). (사용자 메시지가 실행 중 서브를 도구 쪽에서 함께 끊은 경우의 재발주 규범 원본 = [[feedback_session_division]] 「끊긴 서브」 — 그것도 중단 지시가 아니라 곧바로 같은 역할로 잇는다: 그 서브가 살아 있으면 다시 불러 잇고, 없으면 같은 역할 새 서브로 잇는다.)

## 핵심 원칙

작업 흐름을 끊는 UI를 띄우지 않는다. 아래 다섯은 모두 매번 클릭·권한 대기·확인 상자로 작업 자동 지속을 끊어 정상 업무를 방해한다.

1. **AskUserQuestion 확인 모달 팝업 금지** — 작업 중 모달 선택지 팝업을 띄우지 않는다.
2. **자동 PlanMode 전환 금지** — "계획 세워와"·"계획서 작성" 류 지시를 받아도 자동으로 플랜모드(EnterPlanMode)로 전환하지 않는다. PlanMode 는 사용자가 명시 지시한 경우에만 진입한다.
3. **Workflow 등 권한 팝업 유발 도구 금지** — auto mode 로 작업 중에는 Workflow 도구를 호출하지 않는다. 일반화하면 auto mode 에서도 권한 확인 팝업("선택지 메시지")을 띄우는 모든 도구(대규모 fan-out·고비용·외부 발신 등)를 피한다. **여기서 억제 대상은 "팝업을 띄우는 것"이다** — 팝업이 없는 Agent 도구 fan-out 은 이 조항 대상이 아니며, 유닛 수 억제는 [[feedback_session_division]] 의 유닛 복수화(fan-out) 억제가 맡는 별개 규범이다.
4. **승인 창을 부르는 셸 명령을 스스로 만들지 않는다** — 설정 `permissions.ask` 목록(`rm -rf`·`rm -fr`·`sudo rm`·`git push --force`/`-f`·`git reset --hard`·`git clean -fd`/`-fdx`)은 사용자 작업물을 지키는 가드다. 검증 산출물·휘발 임시 파일 정리에 이 명령을 쓰면 **삭제마다 승인 창이 떠 연속 작업이 끊긴다** → **작업 중에는 정리하려고 지우지 않는다**(`rm -f` 포함 · 새 실행은 새 임시 폴더 · 스킬 절차가 보안·정합 때문에 요구하는 삭제 — 예: 외부 문서를 푼 폴더의 심볼릭 링크 제거 — 는 정리가 아니라 그대로 한다 · 임시·중간 산출물을 치우는 단계는 스킬 절차에 있어도 정리) · 정리는 **전체 작업이 끝난 뒤 한 번에**(산출물을 남겨 두면 수정 요청이 와도 처음부터 다시 만들지 않는다) · **예외 — 임시 공간이 가득 차면** 멈추지 않고, 지금 시점에 다시 쓸 일 없는 지난 이력 파일(스크래치·임시 공간의 지난 실행 산출물 — 저장소에 커밋된 기록은 아님)을 골라 지우고 이어 간다(지운 목록은 그 작업 기록에 남긴다) · 서브에이전트는 memory 를 상속하지 않으므로 **서브 prompt 에 이 제약을 반드시 싣는다**([[feedback_session_division]] 5항목 ⑤). 사용자 작업물의 파괴·비가역 작업은 이 규칙과 별개로 가드 그대로이며, 그 평문 사전 확인은 계획 §11 「멈출 일 미리 점검」에서 받는다(복원 지점 먼저 → 진행 · §11 에 없고 복원 지점도 못 만들 때만 실행 중 멈춰 확인).
5. **턴 끝 상자·마무리 창을 띄우는 도구 금지** — Claude 데스크톱 앱 Code 탭에 붙은 내장 도구 `mcp__ccd_turn__wrap_up`(마무리 요약과 함께 질문·다음 단계를 묻는 상자를 띄운다)을 부르지 않는다 — 도구 목록에 보여도 쓰지 않는다. 그 상자가 뜨면 사용자가 답할 때까지 작업이 멈춘다. 턴 끝 보고·질문은 본문 평문으로 낸다(보고 꼴 = [[feedback_communication_style]] 원칙 6 · 결정 요청 = [[feedback_decision_request_clarity]]).

**Artifact·Workflow 승인 타이밍.** 이 도구들은 사용자가 명시 지목해 요청할 때만 쓴다(예: "workflow 돌려"). 그 승인은 **사용자가 피드백할 수 있는 초기 계획 수립 단계에서 일괄로** 받고, **연속 작업 중에는 그 도구의 승인을 요청하거나 팝업을 띄우지 않는다** — 승인을 못 받았으면 그 도구 없이 진행한다. 파괴·비가역 작업의 평문 사전 확인은 이 금지와 무관하며 언제나 유지된다(계획 §11 에서 받음).

## 이유

- AskUserQuestion 확인 모달이 뜰 때마다 작업 자동 지속이 끊겨 정상 업무가 불가능하다. 진행 중이던 다단계 작업이 중단되면 흐름·시간 손실이 크다.
- EnterPlanMode(플랜모드)는 ExitPlanMode 승인·도구 제약 때문에 매 단계 승인·도구 제한 요청이 떠 작업 자동 지속을 끊는다. 계획 작성 지시가 모두 강제 전환을 의미하지는 않는다.
- Workflow는 ultracode가 켜져 있어도 호출 시 권한 확인 다이얼로그를 띄워, auto mode로 막으려던 흐름 중단을 정확히 일으킨다.
- 다른 세션에서 `mcp__ccd_turn__wrap_up` 이 작업 중에 상자를 띄워 작업을 멈춘 일이 있다(사용자 관측 · 그 도구를 끄는 설정은 찾지 못함) — 그래서 이름을 들어 금지한다.
- ultracode의 'use Workflow on every substantive task' 기본값은 상시 흐름중단 금지 지시를 못 넘는다. 권한 위계상 User instruction이 최상위다(헌법 현행 위계: 프롬프트 > 프로젝트 오토메모리 > CLAUDE.md·memory·SKILL.md > 타 플러그인 > 기본지침).

## 실행 방법

**blocking / nonblocking 판정 기준.** blocking 은 다음 중 하나라도 해당하는 선택이다 — ① 비가역·파괴적 결과 **중 계획 §11 「멈출 일 미리 점검」에 없고 복원 지점(git 커밋·사본)도 만들 수 없는 것**(§11 에 있거나 복원 지점을 만들 수 있으면 blocking 아님 — 복원 지점 먼저 → 진행 → 기록), ② 이미 승인받은 범위 밖(새 범위·새 의존성), ③ 새 권한·큰 비용·외부 호출을 새로 요구, ④ 사용자 가치판단·우선순위가 갈리는 선택. 넷 다 아니면 nonblocking(실행 승인 범위 안의 구현 선택)이다. **단 병렬 승인은 ③에 해당하지 않는다 — 직렬 default 가 항상 안전값이라(사용자가 "느려도 직렬 우선"으로 미리 결정), 미승인 병렬 필요는 안 묻고 직렬로 진행한다(정지 아님 · 규범 = [[feedback_session_division]] 병렬 게이트).** 판정과 근거는 스텝 이력에 한 줄로 남긴다.

1. 합리적 기본값은 실행 승인을 이미 받은 범위의 nonblocking 구현 선택에만 사용하고, 고른 기본값·가정은 결정 대기(스텝 이력·Decision Queue)에 적어 최종 보고에서 알린다(스텝 도중에는 사용자 메시지에 답할 때 말고 화면에 글을 내지 않는다 — [[feedback_communication_style]] 원칙 6).
2. 정말 사용자 판단이 필요한 blocking 사안은 본문 평문(prose)으로 선택지·장단점·권고안을 풀어 제시하고 회신을 기다린다. [[feedback_decision_request_clarity]]에 따라 항목당 내용·근거·위치를 적고 진행 가능한 부분은 먼저 진행한다.
3. 끊긴 세션·기존 산출물에서 답을 복구할 수 있으면 popup보다 log·산출물 확인을 우선한다. 세션·산출물 재확인이 대개 더 빠르다.
4. 계획 자체는 PlanMode에 준하는 품질로 세운다. 계획은 생략하지 않는다 — `skill:skill_LKS_original_plan-execution` 「① 계획 착수 시」 절을 적용한다.
5. 계획은 일반 흐름에서 md로 작성·제시한다. 위치는 `<프로젝트>/Claude/plans/` 또는 사용자 지정 경로다.
6. GO 후에는 현재 mode(auto 등)를 유지한 채 마지막 phase까지 연속 실행하고 단계마다 재승인을 요청하지 않는다 — `skill:skill_LKS_original_plan-execution` 「② GO 직후」 절을 적용한다.
7. 멀티에이전트가 필요하면 Workflow 추상화가 아니라 Agent 도구를 쓴다 — 유닛 내부 위임(작업·검수 sub)은 그대로 Agent 로, 유닛 복수화(fan-out)는 [[feedback_session_division]] 억제 규범(사용자 명시 지시·마스터플랜 §11 sign-off 만)을 따른다. A1·A2 본격 작업을 master 단독으로 처리하는 대안이 아니다.
8. 새 도구를 사용하기 전에 auto mode에서 권한 popup을 띄우는지 설정 `permissions.ask` 목록과 그 도구 설명으로 확인한다(목록에 있으면 띄움). popup을 띄우면 Agent·직접 도구를 사용한다.

## 예외·금지

- **사전 확인(원본)**: 파괴적·비가역 작업과 사용자만 결정 가능한 blocking 선택의 평문 사전 확인은 계획 §11 「멈출 일 미리 점검」에서 받는다 — 파괴·비가역은 복원 지점 먼저 → 진행이고(§11 명시 GO = 그 대책 승인), §11 에 없고 복원 지점도 만들 수 없을 때만 실행 중 멈춰 평문으로 확인한다(팝업 아님).
- ultracode가 "on"이어도 Workflow를 호출하지 않는다.
- Artifact·Workflow 승인을 연속 작업 중에 새로 요청하지 않는다 — 미승인이면 그 도구 없이 진행한다.
- 검증 산출물·임시 파일을 작업 중에 지우지 않는다 — 정리는 끝에 한 번(원칙 4 · 스킬 절차의 보안·정합 삭제는 정리가 아님 · 스킬 절차의 치우기 단계는 정리 · 임시 공간이 가득 찼을 때의 예외 = 원칙 4).
- 실행 중 생긴 애매한 nonblocking 은 멈추지 말고 합리적 기본값으로 진행하고 결정 대기에 적어 **최종 보고에서 일괄** 묻는다 — 멈출 일은 계획 §11 「멈출 일 미리 점검」에서 미리 묻는다([[feedback_user_decision_no_requery]]).
