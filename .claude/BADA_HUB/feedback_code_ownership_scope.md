## 적용 조건

사용자가 직접 작성한 코드·컨벤션·범위를 읽거나 수정할 때 적용한다.

## 핵심 원칙

사용자가 직접 작성한 코드·컨벤션·범위를 존중한다. 모두 영구 준수한다.

**1. 사용자 작성 코드의 명명법·컨벤션 절대 보존**
사용자가 "내가 직접 짰다"고 명시한 코드는 식별자(변수/함수/컬럼/상수/메서드명), 대소문자, 표기법, 한글/영어 선택, 정수/문자열 인코딩 방식을 임의로 바꾸지 않는다. 동작·로직 수정은 요청 시 가능하나 명명법은 사용자 컨벤션이 최우선.
- 포함: 컬럼명(사용자가 쓴 PascalCase/Snake_Case 표기 그대로), enum 값(정수 코드로 적었으면 정수 그대로 — 문자열 매핑 임의 추가 금지), 함수·매개변수명(사용자 함수명을 임의 개명 X), 한글 문자열(사용자가 쓴 라벨을 추측 값으로 치환 X), 띄어쓰기·특수문자(중간 대문자 등 사용자 표기 그대로).

**명명·인코딩 권위 3계층 (충돌 해소 순서)**: ① 사용자 작성 코드의 기존 식별자·인코딩(최상위) → ② 프로젝트 자체 컨벤션 문서 → ③ 언어/글로벌 스타일 가이드(PEP 등). 충돌 시 상위 우선 — 상위를 하위로 정규화하지 말고, 하위를 상위에 맞춰 수정한다. 정수/문자열 코드·대소문자·라벨 표기 모두 사용자 사고 모델의 인코딩이므로 보존 대상.
- 자기완결 예시: 특정 컬럼을 정수 코드(예: 1/2/3/…)로 인코딩한 사용자 코드에, 임의로 신규 문자열-매핑 컬럼 + 추측 라벨을 끼우면 위반. 정수 코드·사용자의 대소문자 표기 같은 디테일 그대로 보존.

**2. 지정 범위 외 임의 수정 금지**
사용자가 "X만 수정" / "Y 영역만 변경"식 범위 지정 시 그 범위 외 어떤 영역도 임의 수정 X. 범위 외 미지정이어도 사용자 작성 코드·컨벤션 영역은 모두 변경 시 먼저 묻기.
- 로직 개선 방향성 제안은 OK, 묻지 않고 수정해버리는 행동 금지.
- 다른 영역 개선 후보를 발견하면 작업 종료 부근 보고의 Decision Queue(결정 대기 목록)에만 올린다. "이왕 본 김에"/"이참에" 류 임의 확장 금지.
- **연동부도 범위 밖이면 먼저 묻는다(이 조항이 원본).** 지정 범위 안의 변경이 정상 동작하려면 범위 밖 코드(호출측·연동부)도 바뀌어야 할 때, 그리고 고치기 전 영향 지도([[feedback_change_impact_analysis]])가 범위 밖 사용자 작성 코드·문서를 고칠 곳으로 가리킬 때도 그 자리는 묻기 전에 고치지 않는다 — 영향 지도에는 「함께 고침」이 아니라 「확인만」(이유 = 지정 범위 밖 · 결정 대기)으로 적는다. 계획 단계에서 보이면 계획 §11 에서 묻고, 실행 중 드러나면 고치지 않은 채 결정 대기에 위치·이유·예상 영향·변경 종류를 적고 이어 간다(그 수정 없이는 지정 범위의 변경도 끝낼 수 없으면 사용자만 결정할 blocking — 판정 = [[feedback_flow_interruption]]).

**3. 부분 수정 요청 시 본체 보존**
"X의 Y 부분만/Y 의존성만 제거·수정" 요청 시 X 본체는 보존. 본체를 다른 것으로 대체·삭제 금지.
- X 자체를 들어내야 Y가 해결되는 상황이면 → 먼저 그 사실 명시 + 옵션 제시 후 사용자 GO 사인 대기. 자율 결정 금지.
- "최소 수술" 우선. 동등 대체안 등이 있어도 사용자가 X 명시했으면 X 유지.

**4. criteria/주석 확대해석 과수정 경계**
criteria·코드 주석을 임의로 확대해석해서 새 스키마·기능을 만드는 과수정을 경계한다. 단순 동작을 사용자 의도로 짧게 진행.

**5. 사용자 작성 문서로의 확장**
위 보존 원칙(명명·컨벤션·범위·본체)은 코드뿐 아니라 사용자가 만든 **문서**에도 동일 적용된다. 스프레드시트의 탭명·헤더·지정 입력셀·수식, Word·PowerPoint 템플릿의 스타일·자리표시자 구조는 그 자체가 사용자 컨벤션을 인코딩한 것이므로 임의 재설계·재명명하지 않는다. 기존 파일을 편집할 때는 그 문서의 컨벤션을 정확히 따르며, 이는 각 문서 스킬의 "match its conventions exactly"(예: `skill:skill_LKS_custom_document` `references/xlsx/GUIDE.md`) 규칙과 정합한다.

- generic 예시(save/restore 로직): 저장 시점의 파라미터 집합이 복원 시 그대로 특정 필드로 되돌아가는 단순 흐름을 사용자가 기대할 때, 코드 주석의 "이 필드는 원복 기준으로 보존" 같은 문구를 확대해석하면 재로드 시 사용자 기대와 반대 결과가 된다. 주석의 국소적 의미를 전역 스키마 변경 근거로 부풀리지 말 것 — 단순 유지가 정답이면 별도 분리 영속화·구조 추가 금지, 평문 확인 후 진행.

**6. 새 코드 작성 시 명명 — 사용자 컨벤션 결맞춤 + 자기 서술적(이름만으로 의미 통하게)**
1~5가 "사용자가 만든 것을 안 바꾼다"라면, 이 조항은 "내가 새로 지을 때"의 규칙이다.
- **(상위) 사용자 기존 컨벤션에 결맞춤.** 새 코드·변수·함수·식별자는 사용자의 기존 코드 표기법·명명 패턴·구조에 결을 맞춘다(3계층 ① 우선). 내 습관대로 바꾸지 않는다.
- **(하위) 자기 서술적 명명.** 그 위에서 각 이름은 **이름만으로 뜻을 알 수 있게** 짓는다 — 뜻이 안 드러나는 불투명 축약·정체불명 약어(예: 한 파일짜리 `ALLK`) 금지, 자기 서술적으로(예: `allSkillNames`). 축약은 뜻이 유지되는 선에서만.
- 상위(사용자 컨벤션)와 하위(자기 서술성)가 충돌하면 **상위(사용자 컨벤션)가 우선**한다.

**7. 마스터 모듈에서 명명 규칙 추출·일관 적용 (여러 모듈 코드베이스)**
한 코드베이스에 사용자가 직접 작성한 원본·마스터 모듈(도메인 모델)이 있으면, 그 모듈의 명명 규칙성을 추출해 나머지 모듈에 일관 적용한다 — **새 처방이 아니라 사용자 기존 컨벤션의 추출**이다(3계층 ① 우선의 실행 절차).
- **추출 절차**: 마스터 모듈 전수 read → 분류별(클래스·함수·속성·dict 키·인자·상수) 어휘 표 정리 → 반복 패턴(prefix/suffix·약어·숫자·대소문자 정책) 추출 → 각 규칙을 line 인용으로 검증(인용 못 하면 추측이므로 폐기) → 타깃 모듈 위반·적용 항목 인벤토리 → 사용자 OK 후 일괄 적용.
- **의미 단위 통일**: 같은 의미 식별자를 모듈마다 다른 표기로 두지 않는다(예: `"anode"` vs `'AN'` 혼용 금지).
- **도메인 약어 보존**: 수학·물리·화학·통계 표준 표기·알고리즘 약어는 풀어쓰지 않고 그대로(§1 인코딩 보존과 동일 축).
- 상세 패턴 카탈로그(클래스·함수·변수·dict·prefix/suffix·통계·상수 표기 예시)는 `skill:skill_LKS_original_visual-design` 하위 `references/code-naming-catalog.md`(경로 Read) — **사용자 컨벤션 추출 예시이지 신규 처방이 아니다**.

## 이유

- 사용자가 직접 작성한 코드의 정수코드 컬럼을 무시하고 신규 문자열-매핑 컬럼 + 추측 라벨을 끼워넣어 문제가 된 사례가 있었다.
- 사용자가 직접 정한 변수·함수명을 AI가 임의로 개명한 사례가 있었다.
- 사용자 코드는 사용자의 사고 모델을 그대로 인코딩한 결과이므로 컨벤션 변경은 통제권 침해다.
- 범위를 명시적으로 지정하지 않으면 지정 범위 밖까지 임의 수정해버린 사례가 반복되어 범위 규칙을 도입했다.
- 사용자가 "특정 컴포넌트가 호출하는 하위 기능만 제거"를 요청했는데 그 컴포넌트를 다른 구현으로 대체해 반발을 산 사례가 있었다. 요청은 의존성 제거였을 뿐 본체 교체가 아니었다.
- 내가 지은 변수명이 이름만으로 뜻을 알 수 없어(한 파일에만 있던 불투명 약어) 사용자가 "그게 뭐냐"를 반복해 물은 사례가 있었다 — 읽는 사람이 뜻을 모르는 이름은 이름값을 못 한다.

## 실행 방법

- 변경이 불가피하다고 판단하면 훅·설정·환경 변경도 건드리기 전에 평문으로 먼저 확인한다.
- 사용자 기존 식별자·인코딩을 기준으로 새 코드를 맞추고, 새 이름은 이름만으로 뜻이 통하게 자기 서술적으로 짓는다(불투명 약어 회피).
- 지정 범위 안에서 최소 수술로 처리한다.
- 범위 밖 개선 후보는 실제 수정하지 않고 Decision Queue 에 위치·이유·예상 영향·변경 종류를 적는다.
- 부분 수정에서는 본체를 유지하고 요청된 부분·의존성만 수정한다.

## 예외·금지

- 새 컬럼·dict·함수를 임의로 추가하지 않는다.
- 실수처럼 보이는 부분(예: 특정 자릿수 zero-fill)도 사용자가 직접 지적·수정 요청하기 전까지 그대로 둔다.
- "이왕 본 김에", "이참에"를 이유로 범위를 확장하지 않는다.
- 본체 대체가 불가피하면 그 사실과 선택지를 먼저 제시하고 사용자 GO를 기다린다.
- criteria·주석의 국소 의미를 전역 schema 변경 근거로 확대하지 않는다.
- 심볼 이름 바꾸기(rename)를 글자 일괄 치환으로 처리하지 않는다 — 정의·참조를 심볼 단위로 찾는 도구(language server·IDE 의 rename 기능 등)로 바꾼다. 그런 도구가 없으면 정의·참조를 기계 검색으로 모두 뽑아 목록을 만들고(같은 글자의 다른 뜻 자리 — 문자열·주석·다른 심볼 — 를 가른다) 자리마다 대조해 바꾼 뒤, 바꾼 수 = 목록 수 · 옛 이름이 가리키던 심볼 자리 0(다른 뜻 자리는 그대로)을 확인하고 고친 코드를 실제로 돌린다.
