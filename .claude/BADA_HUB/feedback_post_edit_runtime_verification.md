## 적용 조건

코드 수정 직후 완료를 판단하기 전에 적용한다.

## 핵심 원칙

코드 수정 후 다음 두 항목을 본문 정독으로 확인해야 한다.

1. 의도한 동작대로 작동하는가.
2. 기존 코드의 호출자·연쇄 분기와 정합성이 깨지지 않는가.

import 통과·AST 통과·cold import 통과만으로 "완료" 보고를 금지한다.

**검수 = 실제 구동이 먼저.** 고친 코드와 그것을 쓰는 시험·실행·재현을 실제로 돌려 에러를 잡는다(실행은 고친 쪽 몫 · 명령과 판정 줄은 work_log). 검수 라운드는 실행으로 못 보는 관점만 돈다(코드 갈래별 라운드 원본 = [[feedback_chunked_review]] 「검수 구분」 코드 특례 · 고치기 전 부르는 쪽·불려 가는 쪽 지도 = [[feedback_change_impact_analysis]]).

## 이유

부분 수정 후 이전에 끼워 넣은 가드(예: 값이 > 0인지 검사하는 방어 분기)가 잔존했고, 이후 작업에서 그 가드를 제거하지 못해 사용자가 의도한 단순 흐름(예: 튜플 언패킹 후 인덱스 보정)이 차단된 채 실행이 깨진 상태로 사용자 실사용 환경까지 흘러간 사례가 근거다. 사용자가 현장에서 원인을 찾느라 상당한 시간을 소모했다. 코드 수정 직후 "기존 코드에서 제대로 실행될지, 의도한 대로 구성됐는지"를 확인하지 않은 직접적 결과이며, 사용자 시간 손실은 가장 큰 비용이다. 이 패턴은 [[feedback_full_file_read_required]]와 같은 뿌리다. 부분 정독 + import 통과로 작업 종료를 선언하지 말고 본문 정독 + 호출·연쇄 시그니처 + 시그널 체인까지 확인해야 한다.

## 실행 방법
1. 수정한 함수 / 메소드 / 시그널의 호출자·발신자 모두 본문 정독으로 확인. grep + 결과 라인만 보고 끝내지 말고 호출 컨텍스트(상위 if / try / loop)까지 읽기.
2. 이전 세션에서 끼워 넣은 가드·검사 코드가 사용자 의도 코드를 차단하지 않는지 검토. 특히 defensive guard(None 체크, 0 체크, 빈 문자열 체크)가 사용자 명시 흐름과 충돌하는 경우.
3. 수정이 호출·전달 체인(발신부 → 중간 relay → 수신부)을 건드리면 각 지점의 시그니처·인자 타입·case 보존이 끝까지 정합하는지 본문으로 점검한다(콜백·이벤트 디스패치·시그널/슬롯 등 relay 구조 일반 — 특정 프레임워크에 한정하지 않는다).
4. **검증 단계** = AST·ruff·cold import 는 최소 조건이다. 그 위에 "수정 부위가 실제로 호출되는 모든 경로"의 본문 정독 + 의미 cross-check 가 진짜 검증이며, 도구를 통과했다는 것만으로는 OK 가 아니다. 사용자가 실제로 밟는 워크플로를 처음부터 끝까지 실제로 돌려 결과가 맞아야 OK 다 — 그 환경에서 돌릴 수 없는 부분만 본문 정독으로 따라가 확인하고 그 부분은 미검증으로 적는다(위 「검수 = 실제 구동이 먼저」).
5. **부분 수정 요청**([[feedback_code_ownership_scope]])일 때 더 위험하다 — 본체 보존 의무와 가드 잔존 검토 의무를 동시에 충족해야 한다.

## 예외·금지

- import·AST·ruff·cold import 통과만으로 완료를 선언하지 않는다.
- grep의 호출 위치만 보고 상위 분기·relay·수신 시그니처 확인을 생략하지 않는다.
- 방어용 None·0·빈 값 guard가 사용자 의도 흐름을 막는 상태를 "안전한 fallback"으로 남기지 않는다.
- 부분 수정 요청에서도 본체 보존과 호출체인 검증을 모두 수행한다.
