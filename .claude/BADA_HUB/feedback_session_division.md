## 적용 조건

사용자 산출물을 만드는 본격 작업(사용자 코드 변경, 대형 문서 빌드, 데이터 빌드)을 서브에이전트로 분업할 때 적용한다. 적용 강도는 업무 등급에 연동한다.

- **A1·A2 본격 산출물** = master + 작업 sub + 검수 sub 3-세션 분업.
- **A3·A4**(정형 실무·단순 수정·반복 검수·기계 작업) = 작업 sub 하나로 처리하고 검수 sub 를 두지 않는다(자체검수 1회).
- **경량**(1-line fix·정보 조회·파일 정독·메모리 갱신) = master 직접 — 경량에 한해 3-세션 모델을 강제하지 않는다. **경량인지 애매하면 본격으로 취급한다. 단 사용자가 계획서·마스터플랜 수립을 명시 지시한 작업은 규모와 무관하게 경량으로 분류하지 않는다.** **검수가 찾은 결함의 고침은 한 줄이어도 경량이 아니고 A3(단순 수정)도 아니다(원본)** — 이번 검증에 붙은 작업 A 하나가 한 발주로 고치고(산출을 여러 A 가 만들었어도 · 그 A 가 없으면 같은 역할 하나) 같은 B 가 확인한다(아래 「같은 A ↔ 같은 B」 · 뜻이 안 바뀌는 단순 단어 치환·오탈자만 master).

**규모 예시(판정 보조 — 위 정의·「애매하면 본격」 이 먼저다).**

| 처리 | 예 |
|---|---|
| 경량(master 직접 · 영향 지도는 함) | 오탈자·띄어쓰기 한 자리 · 1-line fix · 파일 조회·정독·한 줄 답 · 사용자가 시킨 memory 갱신 |
| A3·A4 작업 서브 하나(자체검수 1회) | 판단이 들지 않는 몇 줄~수십 줄 — 같은 꼴 여러 자리 치환(뜻 그대로) · 표·목록 갱신 · 포맷 변환 · 집계 · 검색 |
| A1·A2 본격(3세션) | 판단이 드는 몇 줄~수십 줄(코드 로직·문서 뜻·규칙 문구) · 새 파일·규칙·기능 · 사용자에게 가는 문서·코드 · 원인 진단·설계를 문건으로 남기는 일 · 검수가 찾은 결함의 고침(한 줄이어도) · 사용자가 계획을 세우라고 한 작업 |

## 핵심 원칙

**단일 세션이 작업과 검수를 모두 하면 자기 결과를 자기가 검사하는 셈이라 같은 blind spot으로 누락이 남는다**(예: 컨벤션 전제가 통째로 누락). 세션을 분리하면 cross-check가 강제된다. 이것이 3-세션 분업의 존재 이유다.

**★ 유닛 운용 — 동시 1 유닛이 기본값 (fan-out 억제).** 업무의 기본 수행 단위는 **1 유닛 = {master + 작업 서브A (+검수 서브B)}** 다. master는 오케스트레이션·통합·총괄 검수를 맡고 직접 작업자가 아니다. **서브B는 서브A의 종류에 따라 없을 수 있다**(정형·기계 A3·A4 등은 단일 서브, 검수 생략). **동시에는 1 유닛만 운용하는 것이 기본이다** — 억제 대상은 서브 사용 자체가 아니라 **유닛을 여러 개로 동시에 늘리는 fan-out**(ultracode 과다 병렬로 토큰 낭비)이다. 유닛 복수화는 **① 사용자의 명시적 지시**, 또는 **② 마스터플랜 §11 에 사용자가 sign-off 한 병렬**일 때만 늘린다 — 모델이 자의 판단("고가치라서")으로 늘리지 않는다. 단 **병렬(동시 다중 유닛=fan-out)은 모델이 자의로 시작하지 않는다 — 승인 시에만·기본 직렬**(청크 병렬처럼 도는 서브가 2개 이상이면 그것이 곧 유닛 복수(fan-out)다 — "유닛 내부 동시 다중 서브"라는 범주는 없다 · 게이트·carve-out·승인 2경로·6-bound 상세는 아래 「병렬」 절). **단 3-세션 유닛의 작업↔검수 cross-check 는 이 게이트 밖이다** — 검수 서브가 작업 산출을 받아 뒤이어 도는 **순차** 역할 분업이지 동시 병렬이 아니다(3-세션 교차검증은 1 유닛의 정상 구성이다). **병렬 여부가 애매하면 게이트 안으로 간주해 직렬로 가거나 승인을 받는다(tie-breaker · 예외 = 헌법 「주제 이탈」 줄의 단발 무관 조사 위임은 게이트 대상이 아니다)** — '고가치·대형·효율·빠름'은 그 자체로 병렬 사유가 되지 않는다. **fan-out 비용의 실체 — 단순 토큰량이 아니라 「유닛 수 × 역할별 모델(§1 업무등급 A1~A4·B 배정) 비용 + 단일 master 의 통합·총괄 검수 부하」다.** 유닛을 늘릴지 판단할 때 유닛 수만 세지 말고 이 둘을 함께 본다 — 한 master 밑에 유닛을 N개 늘리면 역할별 모델 비용이 N배로 곱해지고 그 N개를 통합·검수하는 단일 master 부하도 함께 커진다.

**★ 같은 A ↔ 같은 B — 유닛은 끝까지 같은 두 서브로 돈다(원본).** 한 유닛 = **작업 A 하나 ↔ 검수 B 하나**다. A 가 만든다 → B 가 검수한다 → **같은 A** 가 B 의 보고를 받아 고친다 → **같은 B** 가 고친 것을 확인한다 — 확인이 끝날 때까지 이 두 서브가 맡는다. 재확인에서 중대·중간이 0 이면(검수[그 갈래의 검수 — ③ 10라운드 · 코드 ③ 3라운드 · 그 밖 한 번]에서 0 이면 고침·재확인 없이) 그 유닛은 끝난다 — 경미는 목록 → 최종 보고 · 끝난 A·B 는 돌지 않아 병렬 셈에 들지 않는다 · 같은 Phase 안의 다음 유닛도 같은 역할 세션을 다시 부른다(context 크기와 관계없이 · 새 세션을 띄우는 때 = 아래 넷). **A 는 B 가 답할 때까지 대기한다**(산출을 넘긴 뒤 다른 일로 넘어가지 않고, master 가 B 의 보고를 가지고 다시 부를 때까지 기다린다 · 대기 중인 A 는 돌지 않아 병렬 셈에 들지 않는다 — 셈 원본 = 아래 「병렬」 절). 같은 Phase 안의 고침·재확인 때 **새 세션을 띄우지 않고 이미 띄운 A·B 를 다시 부른다**(다시 부르면 캐시된 context 를 그대로 써 같은 파일을 다시 읽지 않는다)(부르는 법 = 끝난 서브에 식별자로 이어 보내기 · 부를 서브는 핸드오프 폴더의 세션 대장 그 Phase 절에 적음 — `skill:skill_LKS_original_multi-session-orchestration` 「같은 A ↔ 같은 B 왕복」). 같은 역할의 새 세션을 띄우는 때는 넷뿐이다 — ① 그 역할 세션이 아직 없을 때 ② 세션이 끊겼을 때(컨테이너 재시작 등 · 작업 A 는 끊긴 작업 트리·work_log 를 그대로 두고 새 A 가 그것과 대상 파일을 전문으로 읽어 이어받는다 · 검수 B 는 새 B 가 앞 보고 파일 대신 발주문에 실린 「확인할 결함 목록」과 남은 라운드·관점을 받는다 — 입력 원본 = [[feedback_chunked_review]] 「검수 입력」) ③ 그 세션의 예산(세션에 주어진 토큰 한도)이 바닥났을 때(필요한 파일을 전문으로 넘긴다 — 요약이 읽은 내용을 대신하면 환각 경로가 열린다) ④ Phase 가 바뀔 때(앞 Phase 의 긴 context 를 매 턴 다시 읽는 비용이 새 서브의 입력 재독보다 크다 · 앞 Phase 의 서브는 다시 부르지 않는다). ④ 의 새 서브에는 그 Phase 세부 계획서 · 발주문이 정한 입력 파일 · 처리표 머리 「이미 정한 것」 목록(처리표 판정 · 앞 Phase 들 것까지 · 양식 = `skill:skill_LKS_original_plan-execution` 의 `references/record-formats.md`) · 마스터 플랜 「늘 지킬 제약」 소절 · 지금 Phase 요청 대장 파일(사용자 결정은 처리표에 베끼지 않고 대장을 읽힌다)을 전문으로 넘긴다 — 앞 스텝·앞 Phase 에서 정한 것을 새 서브가 다시 열지 않게. 컴팩션은 새 세션을 띄울 때가 아니다 — 같은 세션이 발주문이 정한 입력을 다시 전문으로 읽고 이어 간다. 일을 context 크기로 미리 나누지 않는다(핵심 입력 자체가 한 context 를 넘을 때만 나눈다). 컴팩션된 세션을 계속 쓸 때는 편집·판정 전에 발주문이 입력으로 정한 파일·기록을 전부 다시 전문으로 읽고 그 범위를 기록한다([[feedback_compaction_recovery]]). **고침은 같은 A 가 한다** — master 는 B 의 인용 줄을 원문에서 확인해 결함을 재현·확인하고, 영향 지도로 고칠 곳을 판정해 같은 A 에 되돌린다(master 고유 몫 ② · 헌법 「방법론 필수」). **진짜 단순한 단어 치환·오탈자만** 서브 없이 master 가 직접 고치고 master 확인으로 끝낸다 — 판정 기준 = 뜻이 바뀌지 않는 고침(오탈자·표기·띄어쓰기)이면서 영향 지도 「함께 고침」이 그 자리 하나일 때다 · 금지↔허용·등급·주체처럼 뜻을 바꾸는 낱말 교체는 해당하지 않아 같은 A 가 고친다 · 같은 검증에 A 가 고칠 결함이 함께 있으면 그 치환도 A 발주에 실어 한 번에 고치고 B 재확인 범위에 넣는다. **B 가 없는 작업(A3·A4)** 은 작업 서브의 자체 확인 그대로다. 재검증 입력·검수 입력의 원본 = [[feedback_chunked_review]] 「재검증」·「검수 입력」 · 왕복 절차 = `skill:skill_LKS_original_multi-session-orchestration` 「3세션 흐름과 반복」.

**세 세션의 역할과 경계**

1. **master (총괄, 사용자가 직접 대화하는 세션)** — 전체 맥락(작업 지시문 원문·인계·사용자 답변/정정·이미지 추출 코드·매뉴얼), 계획·주의점·확인점, 사용자와의 모든 검토·GO 교환을 보유한다. 본격 작업·검수는 직접 수행하지 않고 서브에 위임하되, 서브 결과를 받아 **최종 통합 + 최종 검수**를 책임진다. **핵심·민감·판단이 필요한 읽기는 master 가 직접 한다** — 서브 요약으로 대신하지 않는다. 단 이미지·OCR 판독은 예외로 언제나 판독 서브(`bada-image-reader`)에 위임한다(헌법 「이미지 판독」 줄).
2. **작업 sub (Implementation)** — master가 정리한 명세(대상 파일·라인·로직, 보존 규칙, 컨벤션) 안에서 지정 산출물을 구성하고 자체검수한다. 무변경 영역을 명시받아 그 밖은 손대지 않는다. **작업 sub의 자체검수는 독립 검수 sub를 대체하지 않는다.** 검수 보고를 받아 고칠 때는 보고를 입력 삼아 고치지 않고, 보고가 가리킨 파일을 직접 열어 읽고 고친다 — 그 파일을 context 에 전문으로 갖지 않은 A(새 세션·컴팩션 뒤)는 먼저 전문으로 읽는다.
3. **검수 sub (품질 감사 + 사양 대조 겸임)** — 두 축을 함께 다룬다. ① **품질·정합 축**: linter·cold import·시그니처/시그널 정합·silent failure·컨벤션·누락 변경. ② **사양·의도 축**: 사용자 의도 vs 실제 구현 차이, 인계 미완료 항목 처리 여부, 사용자 정정 반영 여부. 코드 변경은 하지 않는다. 입력은 대상 파일 + 연계 파일 전문이다(원본 = [[feedback_chunked_review]] 「검수 입력」).

**★ 읽기를 서브에 맡기고 요약으로 판단하지 않는다(원본).** 판단과 고침은 **원문을 직접 읽은 세션**이 한다. 서브가 읽은 것을 줄여 넘긴 요약을 받아 판단하면, 그 요약 중계 자체가 정보를 망가뜨리고 환각을 부른다 — 환각의 가장 큰 원인 두 가지 가운데 하나다. 그래서: ① 검수 B 의 보고는 결론 요약이 아니라 **파일:줄 + 원문 인용**이다. ② 보고를 받은 A 는 그 파일을 직접 열어 보고 고친다. ③ master 도 B 의 요약으로 결론 내지 않고 **인용 줄을 원문에서 확인**한다. ④ 조사·분석 서브(A1·A4)의 결과도 master 가 근거 원문(파일:줄·출처 링크)을 확인한 뒤에만 판단에 쓴다. ⑤ 읽기만 맡기는 서브(읽고 요약해 돌려주는 용도)를 두지 않는다 — 읽은 세션이 그 읽기로 판단·고침까지 한다(검수 B 는 판정을 인용으로 돌려주는 역할이라 해당하지 않는다 · 이미지 판독 위임은 판독 결과 원문을 파일로 남긴다).

**master의 통합 책임** — 서브 결과에 충돌·차이가 있으면 master가 사용자 의도·우선순위에 맞춰 **결정한다. 단순 병합은 금지.** 최종 결과(변경분 + 검수 통과 + 사양 대조 OK)를 사용자에게 보고한다.

**Commit = master 전용.** 작업·검수 sub는 commit 권한이 없다 — 작업 sub 는 변경 + work_log 작성만 하고, 검수 sub 는 검수 보고를 반환 글로 돌려준다(읽기 전용 정의라 파일을 쓰지 않는다 · master 가 받아 핸드오프 폴더에 저장). commit·push·merge 타이밍은 헌법 원본을 따른다.

**★ 서브의 정의·방어.** 서브는 **이 세션이 Agent 도구로 띄우는 서브에이전트**다 — 독립 세션(`create_session` 등)을 열어 일을 넘기거나 master 역할을 옮기지 않는다(사용자가 지목할 때만 새 세션을 연다). 서브의 모델·effort 는 **서브 정의 파일**(`components/agents/bada-*.md` → 설치 뒤 `~/.claude/agents/` · frontmatter `model`·`effort`)로 걸고, Agent 호출 인자 `model` 은 넘기지 않는다(넘기면 별칭이 정의를 이긴다). **모델·effort 를 「못 건다·없다」고 말하기 전에 분업 스킬의 선택지 표(표 1·2)를 본다** — 호출 인자 한 곳의 제약을 방법 전체의 부재로 말하지 않는다. **도구 제약 한 줄(예: 「정의 폴더는 세션 시작 때 있어야 읽힌다」)로 우회를 설계하기 전에 실측한다** — 그 세션에서 실제로 어떻게 도는지(정의가 읽히는지·서브가 무슨 모델로 떴는지 `resolvedModel`)를 확인한 뒤 판단한다. 모델·설정·결정을 답하기 전에 요청 대장부터 보는 규범(계획 실행 스킬)과 같은 결이다.

**커밋 규칙 나누기.** 같은 컨테이너에서 Agent 도구로 띄운 서브(작업·검수)는 파일을 함께 보므로 **커밋하지 않는다**. 다른 컨테이너·다른 도구·다른 AI 로 도는 작업자(`create_session`·워크트리·Codex 등)는 **자기 브랜치·워크트리에만** 커밋·푸시하고(메시지에 자기 출처), 통합(작업) 브랜치 반영은 **master 만** 한다(검토 뒤 merge·cherry-pick).

**병렬 — 자의 동시성 게이트.** **게이트 = (carve-out 아닌) 유닛을 2개 이상 동시에 운용하는 것(fan-out)**. **셈은 동시에 도는(live · 지금 일하는) 서브로 한다(셈 원본)** — 반환하고 다시 불리기를 기다리는 서브(B 를 기다리는 A 등)와 유닛이 끝난 서브는 돌지 않으므로 세지 않는다. 한 유닛{master + 작업 A (+검수 B)}의 A·B 는 번갈아 돌아 **한 유닛이 어느 순간 동시에 내놓는 도는 서브는 최대 1개**다 — 그래서 **동시에 도는 (carve-out 아닌) 작업·검수 서브 수 = 동시 운용 유닛 수**이고, **도는 서브가 2개 이상이면 그것이 곧 유닛 2개 이상**이다(한 디스패치든, 앞 유닛이 도는 중 추가 스폰이든 — staggered 포함). 판정은 개념 자기분류가 아니라 이 **관측(도는 서브 수)**으로 한다 — "이건 한 유닛 내부 병렬"이라는 자기라벨은 성립하지 않는다(유닛 내부 A·B 는 번갈아 돌아 도는 서브 2개가 애초에 나오지 않는다 · 청크 병렬처럼 도는 서브 2개↑면 그것이 곧 유닛 복수다). 이런 fan-out 은 모델이 자의로 하지 않고 **승인 시에만** 한다.

- **승인 2경로**: ① **마스터플랜 §11 Decisions Required 에 사용자가 sign-off 한 병렬**(모델이 실행 중 저작하는 페이즈별 세부계획서는 승인 채널이 아니다 — self-authorization 금지) · ② **사용자발 명시 지시**(시점 무관 · 모델이 solicit 하지 않는다).
- **닫힌 carve-out**(이 셋만 · 자의 확장 금지 · 겹쳐 살아도 유닛으로 미계수) = OCR/이미지 판독 위임 · 주제이탈 단발 조사 · 저부하 하향 위임 helper(4경계 충족 시 · 아래 「저부하 하향 위임 carve-out」 절). (3-세션 작업→검수는 애초에 비동시라 유닛 1개 · 게이트 미작동.) 유닛 카운트(= 동시 운용 유닛 수)는 carve-out 아닌 도는 서브만 센다 — carve-out 위임은 겹쳐 살아도 유닛 수에 넣지 않는다.
- **애매하면 게이트 안**(직렬 또는 승인).
- **무중단 우선**: 미승인 병렬 필요가 실행 중 생겨도 **안 묻고 직렬로 진행**한다(느려도 직렬 우선 · 병렬 승인 요청은 GO-후 정지 사유가 아니다 · 비차단 Decision Queue 기록만). 병렬 신규 제안은 **이미 예정된 정지점**(마스터플랜이 원래 둔 사용자 의견 gate)에서만 이후 페이즈 대상으로 한다 — 병렬 위해 **새 정지를 만들지 않는다**.
- **승인된 병렬의 6-bound(캡 아닌 가이드)**: ① 순서·관계 의존성 준수(순서 유관=직렬/순서-인지) · ② **shared mutable state 동시 접근 금지 = 그 상태를 건드리는 서브는 겹치지 않게 순차화(직렬화 · 동시성은 서로 다른[disjoint] 상태일 때만 · 비면제 — 사용자가 열어도 유지)** · ③ 결과가 직렬과 동등(동시성은 지연만 단축 · 다르면 직렬) · ④ degree 는 승인이 정함(상한을 목표로 삼지 않는다) · ⑤ 비용 고지(유닛 수 × 역할별 모델 + 단일 master 통합·검수 부하) · ⑥ master 통합 폭 이내(진짜 병목은 토큰 아닌 master 통합 능력).
- **review-chunking 은 병렬이 아니라 창(청크) 순차 읽기가 기본** — 발견의 합집합은 라운드마다 관점(관점 10개 = 고정 5 프리셋 + 가변 5)과 청크 창을 바꾸는 데서 커지지 동시 실행에서 커지지 않는다. 창 수는 유지하되 병렬만 뺀다(창 수는 라운드 수가 아니다 — 용어 = [[feedback_chunked_review]] 「용어」). 큰 대상도 한 검수 세션이 창을 차례로 읽는다 — 창마다 서브를 따로 띄우지 않는다(창 규율 = [[feedback_review_chunk_discipline]]).

**★ 저부하 하향 위임 carve-out — 하급 helper 로 상급 토큰 낭비 차단 (사용자 명시 허용).** A1·A2 본체 작업 중 나오는 **판단 불요·정형·기계 하위작업**(자료 전처리·포맷 변환·정규화 선작업·집계·파일 분할/병합·대량 단순 치환)에 한해, 높은 effort 로 도는 상급 등급 서브(A1·A2)가 그것을 직접 처리해 생기는 불필요한 토큰 낭비를 없애기 위해 그 하위작업만 **하급 등급 helper 서브(A3·A4 정의 · Opus 5.5 · low effort)** 에 위임한다. 스폰은 상급 서브가 직접 하급 helper 를 스폰하는 **nested 를 우선**하고(서브는 기본으로 대화 아래 3층까지 서브를 띄울 수 있다 — `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), 런타임이 nested 를 지원하지 않으면 **master 중재로 fallback** 한다. 이 위임에 한해 **유닛 내 동시 다중 하급 helper 생존을 허용**한다 — 이는 위 「병렬 — 자의 동시성 게이트」(동시 1 유닛 기본·자의 병렬 금지)의 **좁은 명시 예외**이며, 아래 **4경계를 모두 충족할 때만** 성립한다. 헌법 §1-병렬 줄은 이 규범의 요지이고, 이 절이 상세 원본이다.

- ⓐ **하급 전용** — 동시 스폰 대상은 A3·A4 뿐이다. **동급·상급(A1·A2·B)의 동시 스폰은 이 예외가 아니며 위 「병렬 — 자의 동시성 게이트」(fan-out 게이트)가 그대로 적용된다**(승인 시에만). '토큰 절약'을 이유로 상급·동급 병렬을 정당화하지 않는다.
- ⓑ **대상 한정** — 저부하 잡작업만이다. **판단·설계·본체 구현·검수는 하향 위임하지 않는다.** 위임 산출물은 본체가 소비하는 부속 자료이지 본체 산출물 자체가 아니다.
- ⓒ **위임 정당화 = 비용 하나 · 속도는 정당화 아님.** 세 층을 구분한다. (1) **하향 위임 자체의 정당화 = 비용 하나뿐** — '상급 모델(Opus)이 저부하 잡작업을 직접 하지 않게 한다'. (2) **동시 다중 helper 는 별개의 허가** — 서로 다른 독립 하위작업이면 겹쳐 돌려도 된다. 이는 '동시에 하면 이득'이라서가 아니라(값싼 A3·A4 라 겹치든 순차든 토큰은 같고, 겹침이 막을 이유가 없어서) 허용하는 것이다 — 즉 동시성은 정당화를 요구하는 이득이 아니라 제약 없는 허가다. (3) **속도용 병렬 금지** — 같은 하나의 하위작업을 빨리 끝내려고 N-way 로 쪼개는 속도용 병렬은 금지한다(동시 helper 는 반드시 서로 다른 독립 하위작업일 때만 · '토큰 절약'으로 상급·동급 병렬이나 속도 팬아웃을 정당화하지 않는다). 스폰 오버헤드가 작업량보다 크면 묶어서 순차 처리하거나 상급이 직접 한다.
- ⓓ **shared state 직렬화** — 동시 helper 가 같은 파일·상태를 건드리면 겹치지 않게 순차화(직렬화)한다 — 동시 생존은 서로 다른(disjoint) 하위작업·상태일 때만이다(6-bound ② 와 같은 규칙).

**하향 판정 3문** — ⓐ 판단을 요하는가 · ⓑ 결과가 본체 논리에 직접 들어가는가 · ⓒ 기계로 검증 가능한가. **판단 불요·부속·기계검증 가능**이면 A3/A4 로 하향한다(역방향 금지 — 판단·설계·본체 구현을 비용을 이유로 하급에 넘기지 않는다). **묶음 우선** — 여러 저부하 하위작업은 한 서브에 묶고, 동시 다중 helper 는 위 ⓒ 를 충족할 때만 둔다. **도는 서브 셈** — 이 helper 는 OCR/이미지 판독 위임과 **동렬의 carve-out** 이라 유닛 수에 넣지 않는다(겹쳐 살아도 미계수 · 위 「닫힌 carve-out」의 셋째 항).

## 이유

- 단일 세션이 작업 + 검수를 겸하면 같은 blind spot으로 누락이 남는다(컨벤션 잔재 다수 누락 같은 사고). 세션 분리로 cross-check가 강제되어야 이 계통 결함이 표면화된다.
- 사전 고지(역할·경계·자의작업 금지·attribution) 없이 서브를 돌리면 작업 sub가 brief 범위 밖 문건·commit을 자의로 만들고 그것을 "사용자 별도 작업"으로 허위 표기하는 사고가 발생한다(실제 사례에서 검수 sub의 cross-check로 뒤늦게 적발). 사전 prompt에 경계를 명시하면 발생 자체를 막는다.
- 서브 반환을 침묵 흡수하거나 추정으로 보충하면 컴팩션 환각의 서브판이 된다 — master의 근거는 서브 반환 실물뿐이다.
- 단계마다 새 작업·검수 세션을 띄우고, 창마다 새 서브의 요약을 모아 처리표를 만들고, 그 표를 입력으로 고침을 발주한 작업이 환각과 되돌림을 되풀이해 처음부터 다시 해야 했다. 원문을 읽은 세션이 판단·고침까지 하고, 같은 A·B 가 끝까지 맡으면 이 중계가 사라진다.

## 실행 방법

- **sub spawn 5항목 고지 (필수):** master 가(서브가 helper 를 띄울 때는 그 서브도) 서브를 spawn할 때마다 prompt 첫 머리에 명시한다.
  1. **본 sub의 역할** = 3-세션 모델 중 작업 sub / 검수 sub 중 무엇인지.
  2. **분업 경계** — 작업 sub는 변경만, commit은 master 권한. 검수 sub는 audit + 사양 대조만, 코드 변경 X.
  3. **brief 범위 밖 자의 작업 금지** — 새 문건/표준/commit/메모리/brief 미명시 파일을 자의로 추가하지 않는다. 발견한 추가 작업 후보는 work_log 의 Decision Queue(결정 대기 목록)에 적기만 하고, 실제 작업은 master 결정 + 사용자 GO 이후에 한다.
  4. **허위 attribution 금지** — work_log·commit message·보고문에 "사용자 별도 작업"·"사용자 지적" 같은 사실과 다른 attribution을 쓰지 않는다. 자기가 작성한 것은 자기 출처로 명시한다.
  5. **필요 memory 맥락 주입** — 서브에이전트는 헌법(CLAUDE.md)은 상속하나 **native 메모리 색인(MEMORY.md)·개별 memory 본문은 상속하지 않는다**. 서브가 특정 memory 규범을 따라야 하면(예: 검수 sub의 `feedback_chunked_review`·`feedback_review_chunk_discipline`, 정독 규율 `feedback_full_file_read_required`) 그 요지를 sub prompt 에 실어 주입하거나, 서브가 포인터를 따라 해당 memory 파일을 Read 하도록 명시한다. **기본은 주입이다** — 헌법 인라인 요지가 그 memory 규범을 온전히 담은 경우에 한해 생략하고, 애매하면 주입한다. **흐름 보호 요지는 예외 없이 싣는다** — 승인 창을 부르는 명령(`permissions.ask` 목록 · `rm -rf` 등) 금지 · 작업 중 정리하려는 삭제 금지(새 실행은 새 임시 폴더 · 정리는 master 가 끝에 한 번 · 스킬 절차가 보안·정합 때문에 요구하는 삭제는 정리가 아님). 서브가 이를 모르면 삭제마다 사용자 승인 창이 떠 연속 작업이 끊긴다([[feedback_flow_interruption]] 원칙 4).
- **서브 열화 반환 복구(원본):** 서브가 에러·타임아웃·빈/절단 반환·brief 범위 밖 산출·확신에 찬 오답으로 돌아오면 침묵 흡수하지 않는다. 원인을 명시하고 brief 를 좁혀 **같은 역할에 재-dispatch 한다**(그 서브가 살아 있으면 다시 불러 · 없으면 같은 역할 새 서브). master 가 직접 수행하는 것은 재-dispatch 가 안 될 때뿐이다(정의가 안 읽히는 등 — 그 사유를 기록한다 · 지정 모델 런타임 장애는 master 직접이 아니라 헌법 「배정 폴백·장애」대로 정지·보고). 검수 발견의 고침은 그때도 같은 A 규칙이다(단순 단어 치환·오탈자만 master · 위 「같은 A ↔ 같은 B」). **clean도 종료조건 도달도 아닌 비정상 종료를 clean으로 계수하지 않는다.**
- **끊긴 서브 = 열화 반환(절단) · 중단 지시가 아니다(원본).** **master 는 사용자 메시지를 받으면 같은 턴 안에서 답하고(답 = 그 턴의 마지막 글), 하던 일에 앞서 실행 중 서브의 생존부터 확인한다.** 사용자 메시지가 도구 쪽에서 실행 중 서브를 함께 끊었어도, 그 메시지가 명시적 중단 지시(「멈춰」·「중단해」)가 아닌 한 그것은 사용자의 중단 지시가 아니라 절단된 열화 반환이다 — master 는 다시 띄울지 묻지 않고 곧바로 같은 역할로 잇는다 — 그 서브가 살아 있으면 다시 불러 잇고, 없으면 같은 역할 새 서브로 잇는다(무엇을 넘기나 = 위 「같은 A ↔ 같은 B」 ②). 그 메시지가 명시적 중단 지시일 때만 다시 띄우지 않는다. 재-dispatch 우선은 헌법 「방법론 필수」 master 고유 몫 ④·「§1-commit·열화 반환」과 같은 규칙이고, 사용자 추가 지시가 정지가 아니고 그 메시지에 같은 턴 안에서 답하는 규범은 [[feedback_flow_interruption]] 이다.
- **서브가 읽은 범위를 남긴다:** 작업 A 는 work_log 에, 검수 B 는 보고에 판단의 근거로 읽은 파일·줄 범위(큰 파일은 창마다)를 적는다 — work_log 에 명령은 그대로, 출력은 판정 줄만(통과 = rc·개수 · 실패 = 오류 줄 · 원 출력은 스크래치 경로만 — 스크래치는 휘발이라 판정 근거는 판정 줄 · 기록 꼴 원본 = `skill:skill_LKS_original_multi-session-orchestration` 「세션 2 — 작업 sub」) — master 스텝 이력의 「읽은 범위」 근거다(규범 원본 = [[feedback_full_file_read_required]] 「읽은 범위를 기록한다」 · 양식 자리 = `skill:skill_LKS_original_plan-execution` 2c).
- **master 통합:** 서브 산출은 파일로 남기고(작업 sub 는 스스로 쓰고 · 읽기 전용 검수 sub 의 반환 글은 master 가 받는 즉시 핸드오프 폴더에 저장), 충돌은 master가 결정한다(단순 병합 X). 최종 통합·최종 검수는 master가 직접 수행한다.
- 반복 파라미터·파일 기반 인계 레이아웃·로그 저장 등 운용 절차·양식과 도구/모델 매핑·sub prompt 표준 머리말 예문 등 스폰 실무는 `skill:skill_LKS_original_multi-session-orchestration`(「① 유닛 설계」·「② 첫 스폰 직전」 절)을 따른다. 검수 sub의 라운드·관점·청크 운용 상세는 `skill:skill_LKS_original_review-chunking`.

## 예외·금지

- **단일 세션 자기검사로 독립 cross-check를 대체하지 않는다.**
- commit을 작업 sub에 위임하지 않는다.
- shared mutable state 를 건드리는 서브들을 겹쳐(동시) 돌리지 않는다 — 순차화한다(6-bound ②·carve-out ⓓ 와 같은 규칙 · 동시 생존은 disjoint 상태일 때만).
- 서브의 비정상 종료를 정상 완료로 계수하거나 추정으로 보충하지 않는다.
- 서브가 읽고 줄여 넘긴 요약을 근거로 판단·고침하지 않는다(인용 줄을 원문에서 확인한다).
- 같은 Phase 안에서 같은 역할 세션이 살아 있으면(컴팩션됐어도 · context 가 많이 찼어도) 고침·재확인·다음 유닛을 새 세션에 맡기지 않는다 — 새 세션은 끊겼거나 그 세션 토큰 한도가 바닥났을 때 · Phase 가 바뀔 때만 · 앞 Phase 의 서브를 다음 Phase 에 다시 부르지 않는다.
