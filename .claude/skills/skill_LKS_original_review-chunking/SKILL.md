# Review Chunking

멀티에이전트로 산출물(파일·문서·코드베이스 — 크기 무관 · 아래 「적용 조건」)을 검증할 때, **관점 10개(고정 5 프리셋 + 가변 5)를 라운드마다 하나씩 걸어 검수 범위(바뀐 단위 + 영향 지도 단위) 전체를 한 번씩 보는** 방법. 검증 1회 = 10라운드다(③ 구조 변경 · 다른 갈래는 아래 「갈래별 검수」). 분량 있는 대상은 한 검수 서브가 여러 창으로 나눠 창을 차례로 읽는다(창마다 서브를 따로 띄우지 않는다). `skill:skill_LKS_original_multi-session-orchestration`의 검수 sub가 이 절차를 따른다.

## 적용 조건

본작업 뒤 검증·리뷰 작업에 적용한다 — A1·A2 본격 산출물은 파일 크기와 무관하다(작은 파일[<800줄]은 창 없이 통째로 볼 수 있을 뿐이다 — 검증 강도는 파일 크기가 아니라 변경 갈래[아래 「갈래별 검수」]로 가른다). **A1·A2 본격 산출물 가운데 사용자에게 가는 것 = 이 검증 · 강도는 변경 갈래로 가른다(③ 구조 변경 = 10라운드 · 그 밖 = 아래 「갈래별 검수」 · 어느 갈래든 범위 = 바뀐 단위 + 영향 지도 단위 · A3·A4 = 자체검수 1회).** 갈래 판정 질문·목록·사례의 원본 = `memory:feedback_chunked_review` 「검수 구분」(대상마다 마스터 플랜 Test Plan 「검증 관점」 표의 「갈래」 칸에 적는다).

## 핵심 원칙

> 청크 수치(~500/700줄 창 · 800줄 미만이면서 Read 한 번에 다 보이는 파일만 통째)·통째위임 금지·자기보고 coverage 불신의 **수치 원본 = `memory:feedback_review_chunk_discipline`** · 관점·등급·종료·재검증·진동의 규범 원본 = `memory:feedback_chunked_review`(둘 다 요지 = 헌법 §3).

**용어 3개 — 셋은 곱하지 않는다(검증량 = 라운드 수 · 원본 = `memory:feedback_chunked_review` 「용어」).** 관점 = 대상을 그 눈으로만 보는 검사 초점(관점 10개) · 라운드 = 관점 하나로 검수 범위 전체를 한 번 검토 · 청크(창) = 한 라운드 안에서 나눠 읽는 단위(창 수는 라운드 수가 아님). 검증 1회 = 10라운드다(관점 10개 = 라운드 10개 · "10 × 창 수"가 아니다).

**한 라운드 = 관점 하나로 검수 범위 전체 1회 검토.** 검증 1회 = 10라운드이고, 관점마다 라운드 하나다. **조기 종료 없음 — 10라운드를 다 본다.** 검수 서브 하나가 10라운드와 재검증까지 끝까지 맡는다(라운드마다·창마다 새로 띄우지 않음 · 창 = 아래 「청크 분할 절차」 · 같은 A·B 원본 = `memory:feedback_session_division`). **관점 × 창 × 서브 조합을 채우려고 라운드·서브를 곱하지 않는다** — 창은 한 라운드 안의 읽기 단위일 뿐이다.

분량 있는 파일을 전독하는 라운드(첫 라운드·전독 복원)는 파일별로 여러 청크(~500줄, 최대 ~700)로 나눠 한 검수 서브가 창을 차례로 읽고 창마다 발견·읽은 범위를 적는다 — 창들을 다 읽어야 그 라운드 하나다. 대형 파일(예: 5000줄, 3000줄)을 한 번에 통째로 읽게 하지 말 것. **이유:** 통째로 맡기면 "100% 정독 완료"라고 보고해도 실제 이해에는 누락이 남고, 창마다 서브를 따로 두면 그 요약을 모아 판단하게 돼 정보가 망가진다.

## 실행 방법

### 관점 10개 — 고정 5 프리셋 + 가변 5

**고정 5 = 검증 대상의 종류로 고른 프리셋 하나(P1~P6)의 관점 다섯.** ③ 은 대상이 **신규**(전부 새로 쓴 것)면 **연결**, **수정**(기존 파일을 고친 곳이 하나라도 있음)이면 **연계**로 고른다 — 어느 쪽인지는 마스터 플랜 Test Plan 「검증 관점」 표에 대상마다 적는다(검수 서브가 스스로 고르지 않는다).

- **연결(신규·수정 공통)** = 안(앞에서 정의·도입한 것을 뒤에서 맞게 쓰나) + 밖(이 산출물이 기대는 기존 것과 맞나).
- **연계(수정)** = 연결 + 바뀌거나 더한 것에 **기대는 곳**(부르는 곳·가리키는 곳·같은 규칙을 적은 곳·예시·잠근 시험·덱) + **수정 전후 호환**(기존 사용법·호출자). 판정 = 변경 목록 + 발주문에 실린 영향 지도 표(master 가 확인한 것 · 작업 기록 통째가 아님) → 기대는 곳만 열어 대조(패키지 전체를 뒤지지 않음 · 지도 밖 연결이 의심되면 근거와 함께 「지도 밖 연결」로 보고) → 어긋난 곳(양쪽 파일:줄 · 코드면 실행 출력) — 이 판정 방법의 원본이 여기다(입력인 영향 지도의 원본 = `memory:feedback_change_impact_analysis`).

**가변 5 = 그 프로젝트의 핵심 위험** — 마스터 플랜 Test Plan 「검증 관점」 표에 미리 적는다. 후보 목록 = 코드 10차원 · 문서 렌즈셋(`skill:skill_LKS_original_plan-execution` phase audit) · 역방향 오독 T1~T10(`skill:skill_LKS_original_instruction-architecture` 의 `references/reverse-misread.md`) · 작업별 예(비동기·UI·파일 I/O·데이터 모델·성능·외부 연동). **섞인 대상** = 주된 종류의 프리셋을 쓰고, 다른 종류에서 가장 다른 항목을 가변 5 에 넣는다(종류마다 검증을 곱하지 않는다).

### 청크 분할 절차

1. 대상 파일의 라인 수를 먼저 확인한다.
2. ~500줄 단위로 창을 분할한다. 예: 5000줄 파일 ≈ 9~10창, 3000줄 ≈ 6창, 1500줄 ≈ 3~4창, 800줄 미만 ≈ 1~2창(줄이 긴 파일은 Read 가 잘라 보이면 줄 수와 관계없이 더 잘게).
3. 전독하는 라운드(첫 라운드·전독 복원)는 한 검수 서브가 창을 차례로 그 범위의 전 라인을 head→tail 정독하고, 창마다 신규 결함과 읽은 범위를 적는다 — 창들을 다 읽어야 라운드 하나다.
4. "100% 읽었다"는 에이전트 자기보고를 신뢰하지 말고, 청크 크기로 thoroughness를 강제한다.
5. **정독 입도 — 첫 커버 전독 / 이후 라운드 필요한 곳(고친 뒤 재검증은 전문 · 아래 「에이전트 프롬프트 규율」).** 그 구간을 처음 읽는 라운드(첫 커버)는 위 3처럼 head→tail 전독하고, 이후 라운드는 **그 관점에 필요한 곳**(직전 변경 지점[diff 가 길잡이] + 그 관점이 짚는 자리 + 문맥 앞뒤 절)만 다시 보고 나머지 미변경 구간은 **기계 검사**(카운트·합계·경로 존재·표기 파싱)로 커버한다. 단 **직전 전독을 context 에 갖지 않은 새 서브가 그 구간을 맡으면 전독**한다 — 새 서브에는 대상 파일 + 연계 파일을 전문으로 넘기고 기록·diff 로 발췌를 대신 맡기지 않는다. 컴팩션·세션 재개도 같은 리셋(전독 복원)이다. 정독 입도 규범 원본 = `memory:feedback_chunked_review` 「정독 입도」.

### 매 라운드 관점 전환 · 청크 스킴 전환

라운드마다 **관점 하나**를 걸고, 같은 산출물을 다른 창(크기·경계·나누는 방식)으로 나눈다 — 전체 통독 / 절·블록별 / 식·함수 단위 / 라인 단위 / 도메인 그룹 등. 한 관점·한 청크 스킴이 놓친 결함을 다른 관점·다른 스킴이 잡는다. 창은 그 라운드 안의 읽기 단위이며 라운드 수를 늘리지 않는다.

- **coverage missing = 0**: 검수 범위의 전 영역이 어떤 라운드에선 반드시 head→tail로 커버되어야 한다.
- **거친 단일 청크는 또 다른 실패축이다.** 분량 큰 구간을 전독하면서 겨우 2청크로 읽으면 발견이 턱없이 적다. 절·블록마다 좁은 창으로 나눠 **순차로** 읽는다(청크 수는 유지·병렬만 제거 · 동시 병렬 검수는 헌법 §1-병렬 게이트[승인 시에만] 대상).
- 전독하는 라운드의 창이 거칠었다고 보이면 **그 라운드 안에서** 창을 절·블록 단위로 다시 나눠 읽는다 — 라운드·검증을 더하지 않는다(10라운드 뒤의 추가 확인은 재검증[같은 검수 서브가 바뀐 단위 + 영향 지도 단위 전문 1회 대조]뿐). 부실 원인이 컴팩션 소실인지 구조적 deferral인지는 git·원천 대조로 정직하게 진단한다.

### 에이전트 프롬프트 규율

각 검수 에이전트 prompt에 다음을 명시한다:

- **갈래(①–④ · 코드 여부)와 검수 범위** — Test Plan 「검증 관점」 표에서 옮겨 싣되 master 가 작업 뒤 실제 diff 로 무거운 쪽으로만 올린 값 · 검수 범위 = 바뀐 단위 + 영향 지도 단위(파일:줄 목록) · ①·②·④·코드면 라운드 관점 대신 그 갈래의 검수 항목(목록 원본 = `memory:feedback_chunked_review` 「실행 방법」)과 영향 지도 대조·「지도 밖 연결」 찾기 · diff 가 칸과 어긋나면 발견으로 보고(원본 = 같은 memory 「검수 구분」).
- **이번 라운드의 관점 하나**(③ 구조 변경) — 고정 5 가운데 하나(고정 ③ 은 신규 = 연결 / 수정 = 연계) 또는 가변 5 가운데 하나. 그 관점의 보는 것·판정 방법을 함께 싣는다.
- **refute mandate** — 통과시키려 하지 말고 반증하려 하라.
- **빈 통과 금지** — "문제 없음"만 반환하지 않는다. 중대·중간이 0이면 그 사실과 읽은 범위·반증 시도를 함께 기록한다.
- **결함 등급 정의** — 중대(정상 실행 안 됨 · 뜻 반전으로 오해 · 큰 흐름 깸) · 중간(실행·흐름은 안 깨지지만 실제로 쓸 때 헷갈려 잘못 쓰거나 우회 필요 — 누가·어떤 상황에서·무엇을 잘못하게 되는지 한 줄로 적을 수 있을 때만 · 못 적으면 경미) · 경미(문구·다듬기·더 나은 방식 — 판정·뜻·실행을 바꾸지 않는 표기·조사 지적은 경미도 아니고 결함으로 세지 않는다). 검수 서브가 붙인 등급은 **제안**(master 가 재현·확인 후 확정). 동작에 대한 주장은 **파일:줄 근거**가 있어야 결함으로 센다.
- **입력 = 대상 파일 + 연계 파일만 · 전문** — 파일 단위로 넘기고(자리·줄 범위만 넘기지 않는다) 패키지 전체·대상 밖 기록(작업 기록 전부·앞 보고 전부)은 싣지 않는다 · 영향 지도 표는 발주문 안에 싣고, 검수 서브는 그 표를 대조해 「지도 밖 연결」을 한 항목으로 찾는다 · 신규 산출물의 연계 파일 = 그 산출물이 기대는 기존 파일(원본 = `memory:feedback_chunked_review` 「검수 입력」).
- **보고 형식** — 첫 줄 = 등급별 수(「중대 n · 중간 m · 경미 k」 · 없으면 「중대·중간 없음」) · 중대·중간마다 파일:줄 · 무엇이 깨지나 · 근거(원문 인용 — 요약 아님 · 재현 출력) · 연결돼 보이는 곳 · 원래 있던 것인지 · 경미 한 줄씩(검증 1회 5건까지 · 나머지는 개수만 · 표기·조사 지적은 넣지 않음) · 창마다 읽은 범위(줄) · 중대·중간이 0 이면 읽은 범위·반증 시도. **수정안 칸 없음**(고칠 곳 판정 = master 영향 지도 · 고침 = 같은 작업 A).
- **범위 고정** — 고칠 곳은 중대·중간 자리 + 영향 지도 「함께 고침」뿐. 원래 있던 결함(이번 변경이 들이지 않음)은 따로 표시하고, 범위 밖 관찰·경미는 목록만 → 최종 보고. 사용자가 이번 작업에만 적용한다고 밝힌 운용 지시를 상시 지침으로 넓히지 않는다(작업 한정을 밝히지 않은 일반 원칙·지침 위반 지적은 지침 반영 계획으로 · 조금이라도 애매하면 최종 보고에서 한 번 확인 · 원본 = `skill:skill_LKS_original_instruction-architecture` §14 원칙 9).
- **작업 기록을 넘기고 재실행을 막는다** — 그 대상의 실행 출력 절(work_log·스텝 이력에 적은 명령과 판정 줄) 경로만 프롬프트에 싣고(작업 기록 전부를 읽히지 않는다) "이미 돌린 테스트는 다시 돌리지 말고 기록으로 판정 · 실행은 기록이 없거나 어긋날 때만"을 명시한다.
- **지정 파일을 창 단위로 차례로 head→tail 정독한다**(첫 라운드 전독 / 이후 라운드는 diff 를 길잡이로 필요한 곳).
- **「이미 정한 것」 목록을 발주서에 싣는다** — 앞 검증·수정에서 정한 것과 그 이유(원래 의도)를 처리표(검수 발견 처리표 · 양식 = `skill:skill_LKS_original_plan-execution` 의 `references/record-formats.md`)에서 옮겨 함께 넘긴다. 그 목록에 든 것을 다시 바꾸자는 지적은 그 이유가 틀렸다는 근거(파일:줄·실행 결과)가 있을 때만 결함으로 세고, 근거 없이 되돌리자는 지적은 결함이 아니다(발주서 틀·결정 고정 · 규범 원본 = `memory:feedback_chunked_review`).
- **재검증은 같은 검수 서브가.** 10라운드를 본 그 서브를 다시 불러 바뀐 단위 + 영향 지도 단위를 전문으로 읽게 하고 diff·직전 발견 위치를 길잡이로 싣는다 — 범위·800줄 미만 전문·새 서브에 넘길 것(「확인할 결함 목록」·남은 라운드·관점) 원본 = `memory:feedback_chunked_review` 「재검증」·「검수 입력」 · 새 세션을 띄우는 때 = `memory:feedback_session_division` 「같은 A ↔ 같은 B」 · 컴팩션된 서브 = `memory:feedback_compaction_recovery` 「컴팩션된 서브」.

## 검증

### 10라운드 · 한 번에 고침 · 재검증 · 진동

- **③ 구조 변경: 검증 1회 = 10라운드(관점 10개) · 조기 종료 없음 · 범위 = 바뀐 단위 + 영향 지도 단위.** 10라운드를 다 본다. 라운드 수는 이것이 전부다(관점·창 조합 수로 늘리지 않는다). 규범 원본 = `memory:feedback_chunked_review`(요지 = 헌법 §3).
- **갈래별 검수(①·②·④ · 코드).** 같은 검수 서브가 그 갈래의 검수를 한 번 한다(① 기계 대조 + 뜻·유의어 자리 판정 · ② 바뀐 줄 + 지도 줄 + 적대 항목 하나 + 연계 확인 · ④ 실행 게이트 + 바뀐 줄 · 코드 = 실행 먼저 · 코드 ③ 3라운드) — 판정·항목·사례 원본 = `memory:feedback_chunked_review` 「검수 구분」. 입력·등급·보고·한 번에 고침·재검증·진동은 10라운드와 같고, 사용자가 요청하면 어느 갈래든 10라운드로 본다.
- **그 갈래의 검수(③ 10라운드 · 코드 ③ 3라운드 · 그 밖 한 번)를 다 본 뒤 한 번에 고친다.** master 가 인용 줄을 원문에서 확인해 중대·중간을 재현·확인 → 영향 지도(`memory:feedback_change_impact_analysis`) → 이번 검증에 붙은 작업 A 하나가 함께 고칠 곳 전부를 한 발주·한 변경으로 수정(산출을 여러 A 가 만들었어도)(진짜 단순한 단어 치환·오탈자만 master 직접) → 확인 가능한 출력 인용 빌드/검증 → ledger 기록. **경미는 고치지 않고** 목록 → 최종 보고(5건까지).
- **재검증.** 같은 검수 서브가 바뀐 단위 + 영향 지도 단위를 전문으로 한 번 대조한다(입력·범위·800줄 미만 전문·새 세션일 때·master 확인으로 끝내는 경우 · 원본 = `memory:feedback_chunked_review` 「재검증」).
- **수정 검수·시험 범위.** 이미 통과한 시험은 다시 돌리지 않는다(고친 뒤 바뀐 부분 확인은 아래 범위의 수정 시험) · 수정 검수·시험은 바뀐 부분과 그 부분을 가져다 쓰는 연계 부위 전부에만 하고 수정 적용 이전 앞단(바뀐 것에 기대지 않는 앞 단계)은 뺀다(다시 시험·검사하지 않음 · 바뀐 코드가 기대는 입력을 만드는 쪽은 꼴 대조로 읽음) · 역테스트는 설치기·점검기·도구 코드가 바뀐 때만 바뀐 것과 그것을 쓰는 검사를 돌린다(문구만 바꾼 곳은 없음) · 원본 = `memory:feedback_chunked_review` 「수정 검수·시험 범위」.
- **진동.** 재검증에서 중대·중간이 직전보다 줄지 않으면 곧바로 **원인 수정으로 전환**(진동 판정은 횟수로 하지 않는다 · 멈추지 않는다 — 재작업 왕복 한도 max_iter 는 분업 스킬이 따로 센다 · 덧대기 중단 · 영향 지도 전체 재조사 · 공통 원인을 고침) → 재검증 계속. 원인 수정 뒤에도 남으면 Result·최종 보고에 싣고, 그 결함이 걸린 산출(예: 릴리스 zip)은 만들지 않고 최종 보고에서 결정한다.
- **비용 기록.** 검증·재검증마다 중대·중간 수·서브 비용 네 종류(캐시 안 된 입력·캐시 쓰기·캐시 읽기·출력)·시간을 적고 최종 보고에 추세로 싣는다(자리 = Ledger 가 있으면 그 Phase 행 Validation 열 · 없으면 그 검증·재검증 스텝 이력 「게이트」 항목 · 양식 원본 = `skill:skill_LKS_original_plan-execution` 의 `references/record-formats.md`).
- **같은 지점 연속 두 번 지적 = 재판정** — 고치기 전에 진짜 문제인지 다시 판정한다(진짜면 원인을 고치고, 아니면 기각하고 근거를 규범 면에 남긴다 · 재판정 원본 = `memory:feedback_change_impact_analysis` 원칙 6). 되돌림을 채택하면 진행 표 결과 칸에 「되돌림」으로 적는다(되돌림·결정 고정 원본 = `memory:feedback_chunked_review`).
- 종료 후에도 "남은 중대·중간 없음"은 정독을 전제로만 유효하다(입도 원본 = `memory:feedback_chunked_review` 「예외·금지」).

## 예외·금지

- 대형 파일을 한 번에 통째로 읽게 하지 않고, 창마다 서브를 따로 띄우지도 않는다 — 한 검수 서브가 창을 차례로 읽는다(창 하한·통째 허용 기준의 수치 원본 = `memory:feedback_review_chunk_discipline`).
- "100% 읽었다"는 에이전트 자기보고만으로 coverage를 확정하지 않는다.
- 분량 큰 구간을 거친 단일 청크나 겨우 2청크로 검증하지 않는다.
- **조기 종료 없음(10라운드를 다 본다) · 관점 × 창 곱셈은 하지 않는다.** 반증(refute)으로 찾는 태도는 유지한다.
- 관점 × 창 × 서브 조합을 채우려고 라운드·서브를 곱하지 않는다(라운드 하나 = 관점 하나로 검수 범위 전체 1회). 발견 건마다 반박 서브를 따로 띄우지 않는다 — 발견 검증은 master 삼각검증(실물 재현)이고 수정은 묶어서 같은 작업 A 가 한다.
- **다른 스킬과 겹칠 때** — 다른 스킬이 자체 검증 횟수·절차를 요구해도 같은 대상 검증은 한 번(이 절차) · 그 스킬의 표기 규칙(구획 마커·주석·독스트링)만 적용한다.
