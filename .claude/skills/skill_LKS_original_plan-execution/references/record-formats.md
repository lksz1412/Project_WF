> `skill:skill_LKS_original_plan-execution` 이 지시하는 지점에서만 참조한다. **Result 항목·Ledger 열 목록의 원본이 여기다**(양식·스키마·표) — 개수·필수·규율·포인터는 SKILL.md가 소유한다. 상시 로드 예산에서 빼기 위한 progressive disclosure(instruction-architecture `references/` 패턴).

## Result 12항목

Summary / Step Range / Inputs / Files Created / Files Updated / Read Coverage / Execution Evidence / Validation·Gate·Confirmed / Non-Changes / Open Issues / Decision Queue / Next

(Decision Queue = 결정 대기 — 그 Phase 의 스텝 이력·work_log 결정 대기를 모은 것 · 정의 원본 = `memory:feedback_confirmed_items_policy`)

Read Coverage에 실제 읽은 범위를 행/페이지로 명시하지 못하면 "정독했다"는 주장은 무효.

다시 적지 않는다 — Execution Evidence·Validation·Gate·Confirmed 같은 항목은 그 Phase 의 종합(결론·게이트 결과)과 근거가 든 스텝 이력 경로만 적는다(스텝 이력의 결정 내용·영향 지도·명령 출력을 옮겨 적지 않음 · 스텝 이력은 다시 영향 지도 전 행이 든 기록[work_log·발주문 — master 가 스텝 이력에 직접 두었으면 그 스텝 이력]과 판정 줄이 든 기록[work_log — master 가 직접 실행했으면 그 스텝 이력]을 가리킴). Read Coverage 의 파일·행 범위 명시는 그대로다.

## Ledger 12-column (장기 작업: phase≥3 또는 step≥20)

`| Phase/Subphase | Planned Steps | Actual Steps | Block | Purpose | Status | Plan | Result | Machine Artifacts | Validation | Gate | Next Step |`

컬럼: Phase 식별자 / 계획 step 범위 / 실제 수행 범위 / 의미 목적(setup·inventory·refactor·audit) / 한 줄 목적 / PASS·FAIL·IN_PROGRESS·BLOCKED / 계획서 경로(마스터 플랜 + 그 Phase 세부 계획서 파일) / result 경로 / companion JSON·빌드 산출 / gate PASS 근거 요약(그 Phase 에 검증·재검증이 있었으면 회차마다 중대·중간 수·서브 비용 네 종류[캐시 안 된 입력·캐시 쓰기·캐시 읽기·출력]·시간도 여기에) / gate 식별자 / 다음 cumulative step. 본 용도: 컨텍스트 압축·세션 교체·재개를 위한 복구 지점(Save-point).

Ledger 가 없는 짧은 작업의 검증·재검증 비용(중대·중간 수·서브 비용 네 종류·시간)은 그 검증·재검증 스텝 이력의 「게이트」 항목에 적는다(비용 기록 규범 원본 = `memory:feedback_chunked_review`).

## 완료 주장 유형별 검증표

오른쪽 칸("불충분") 근거로 왼쪽 칸 주장 시 gate 미통과.

| 완료 주장 | 실제 필요한 증거 | 불충분한 근거 |
|---|---|---|
| 테스트 통과 | 테스트 출력: failed 0 | 이전 결과, "통과할 것 같음" |
| Lint 클린 | Lint 출력: error 0 | 부분 점검, 추정 |
| 빌드 성공 | 빌드 exit code 0 | "lint 통과했으니 빌드도 될 것" |
| 버그 수정됨 | 증상 재현 테스트 통과 | 코드만 바꾸고 "고쳤다고 가정" |
| 회귀 테스트 유효 | red→green 사이클로 직접 검증 | 통과 1회만 확인 |
| sub-agent 작업 완료 | VCS diff로 실제 변경분 확인 | "성공했습니다" 보고만 신뢰 |
| 요구사항 충족 | 항목별 체크리스트 대조 | 테스트 통과만으로 충족 간주 |

## 사용자 요청 대장 (본격 작업 · 사용자 발화 추적)

위치: Phase 마다 파일 `Claude/results/REQUEST_LEDGER_phase<ID>.md`(Phase 구분 없는 작업은 파일 하나 `Claude/results/REQUEST_LEDGER.md`) — Phase 파일들을 합쳐 요청 대장이다. 본격 작업에서 사용자 발화(요청·지시·결정·수정)를 한 행씩 쌓아, 지침에 반영했는지·어디에 반영했는지·마스터 플랜과 세부 계획서에 반영했는지를 추적한다. 사용자 결정의 원본·이력은 이 대장이다 — 결정이 기획 내용을 바꾸면 마스터 플랜의 그 자리에 반영하고 이 대장 행에 체크하되, 대장을 마스터 플랜에 통째로 옮겨 적지 않는다. 마스터 플랜·Result·스텝 이력과 별개 축이다 — 그 셋은 실행 기록이고, 이 대장은 사용자 요청 원본이다.

행 = `| 번호 | 일시 | 받은 시각 | 요청 요지 | 반영 위치 | 마스터 플랜 반영 | 세부 계획서 반영 | 상태 | 근거 |`
- **번호** = 요청 순서대로 단조 증가(`R<n>`). 건너뛰지 않는다.
- **일시** = 적기 직전에 시계(`date`)로 확인한 시각 — 어림 표기(`15:0x` 류) 금지(원본 = SKILL.md 2c).
- **받은 시각** = 세션 기록의 그 사용자 발화 시각(대기열 등록 또는 사용자 행) — 「일시」(적은 시각)와 따로 적는다.
- **요청 요지** = 사용자 발화를 한 구로(원문 인용은 근거 칸).
- **반영 위치** = 어느 파일·단위·Phase/Step 에 반영했는지(파일:줄 또는 Phase/Step).
- **마스터 플랜 반영 · 세부 계획서 반영** = 그 요청으로 마스터 플랜(그 요청이 바꾼 기획 내용의 자리)·그 Phase 세부 계획서(스텝)를 고쳤으면 `✅` + 고친 자리, 고칠 것이 없으면 `—`. 행은 지우지 않고 이력으로 남긴다(대장을 마스터 플랜에 통째로 옮겨 적지 않음 · 원본 = 이 행).
- **상태 기호** = `✅` 반영 완료(근거 확인) · `🔄` 진행 중 · `⏳` 예정(계획에 있음) · `↪` 다른 요청으로 대체 또는 작업 한정(아래 처리 갈래 (나) — 근거 칸에 사용자 원문 · 끝난 `↪` = 대체된 행 · 그 작업이 끝난 작업 한정 행).
- **근거** = 사용자 발화 위치(세션·메시지)나 반영 커밋·Result.

규율:
- **행 삭제 금지 · 상태만 갱신** — 해소된 요청도 행을 지우지 않고 상태 칸만 바꾼다. 무엇을 언제 왜 반영했는지가 남아야 다음 발주서의 「이미 정한 것」이 된다.
- **Phase 마다 새 파일** — Phase 착수 때 새 파일을 열고 앞 Phase 파일의 끝나지 않은 행만 이어 적는다(번호·칸 그대로 · 앞 파일은 그대로 둔다). 지난 Phase 파일을 읽는 때 = 마스터 플랜을 작성·갱신할 때 · 사용자가 제시안을 요청할 때 · 사용자가 지난 결정을 물을 때 · 컴팩션 대조에서 지금 파일에 없는 메시지를 확인할 때 · Phase 착수 때 끝나지 않은 행을 이어 적을 때(앞 Phase 파일 하나).
- **답하기 전에 대장부터** — 사용자가 이미 말한 사실(모델·설정·결정)을 답하거나 제안하기 전에 지금 Phase 대장 파일을 먼저 본다(이미 정해진 것을 다시 묻지 않기).
- **받은 그 자리에서 적는다** — 다음 발주·편집 전에 적는다(적는 시점 원본 = SKILL.md 2c-2).

### 「늘 지킬 제약」 절 — 제약마다 처리 갈래

마스터 플랜 Current Ground Truth 아래에 소절 「늘 지킬 제약」을 두고(11 섹션 이름·순서는 그대로), 사용자 명령을 **제약으로만 적어 두지 않는다** — 명령마다 아래 처리 갈래를 정해 함께 적는다:

| 갈래 | 판정 | 처리 |
|---|---|---|
| (가) 일반 규칙 | 이 작업만이 아니라 앞으로도 적용될 규칙 | **지침 반영 계획**을 세운다 — 어느 단위(헌법·memory·스킬)·어느 파일에 넣을지 |
| (나) 작업 한정 | 사용자가 이 작업에만 적용한다고 밝힌 것 | **작업 한정**으로 적고 근거 원문을 남긴다(넓히지 않는다) |
| (다) 애매 | 일반인지 작업 한정인지 불분명 | 그 작업에만 쓰고, 결정 대기 목록에 「지침에 넣을지」로 올려 **최종 보고에서 묻는다** |

갈래 없이 「제약」으로만 적어 두면 일반 규칙이 작업 한정으로 묻혀 지침에 반영되지 않는다(재발 방지). (다) 처리는 「작업 한정 지시」 규범(원본 = `skill:skill_LKS_original_instruction-architecture` §14 핵심 원칙 9)과 같은 규칙이며, 이 양식은 그 판정을 대장에 적는 자리다.

## 검수 발견 처리표 (검증마다 · 「이미 정한 것」의 자리)

위치: 그 유닛의 핸드오프 폴더 `Claude/results/handoffs/<task-name>/TRIAGE_phase<ID>.md`(Phase 마다 새 파일 · 검증마다 한 절). 파일 머리에 「이미 정한 것(지금까지 누적)」 목록을 둔다 — 처리표 판정(무엇을·왜)만 담는다. 새 Phase 파일은 Phase 착수 때 한 번 앞 Phase 파일 머리의 목록을 이어 받는다 — Phase 가 바뀌어 띄우는 새 서브에 넘기는 그 목록이다(원본 = `memory:feedback_session_division` 「같은 A ↔ 같은 B」 ④). master 가 검수 보고(③ 구조 변경 = 10라운드 · 그 가운데 한 라운드가 적대 관점 / ② 국소 변경 = 적대 항목을 둔 한 번 검수 / ①·④·코드 = 갈래별 검수)를 받아 인용 줄을 원문에서 확인한 뒤 고칠지·어디를 고칠지 판정해 적는 표다 — 수정마다 남기는 「무엇을·왜(원래 의도)」의 자리가 여기고, 다음 발주서의 「이미 정한 것」은 이 표에서 옮긴다(규범 원본 = `memory:feedback_chunked_review` 「master 통합」). 사용자 요청 대장(사용자 발화)·Ledger(Phase)·세션 대장(서브 목록)과 다른 축이다.

행 = `| # | 라운드 | 결함(보고 원문 파일:줄 인용) | master 확인 | 판정 · 고칠 방향(원본 자리) | 근거 |`
- **master 확인** = 인용 줄을 원문에서 확인했나(✅ · 재현 안 되면 오적발로 적고 판정 칸에 「기각」 + 근거).
- **판정 · 고칠 방향** = 고침(원본 자리 · 영향 지도는 고칠 A 발주서에) / 경미(목록 → 최종 보고) / 기각 / 되돌림(재판정을 거친 것만 · 진행 표 결과 칸에도 「되돌림」).
- **근거** = 방향 문건·사용자 결정·규범 줄(파일:줄).
- 표 아래 = 경미 목록 · 알려진 것(결정 대기) · 검증 비용(중대·중간 수·서브 비용 네 종류·시간).

규율: 행 삭제 없이 상태만 갱신한다 · 고침이 끝나면 그 행에 무엇을 바꿨는지(파일:줄)와 재확인 결과를 더한다 · 대화에만 두지 않는다(컴팩션 뒤 복구 읽기 = `memory:feedback_compaction_recovery` 「복구 읽기 순서」).

## 결과 문건 보호 — 정정 패턴

| 패턴 | 파일명 | 사용 시점 |

| Supersession | 구: `..._SUPERSEDED_BY_<new>.md` / 신: `PHASE_M_..._RESULT.md` | 기존 부정확, 처음부터 재작성. 구 result 삭제 금지 |
