### 1-a. MIT 자료에 대한 저작권 고지 (필수)

```
MIT License · Copyright (c) 2026 Gabberflast
https://github.com/Gabberflast/academic-pptx-skill
```

**`content_rules.md`는 위 MIT 자료의 파생물로 본다.** 초판을 작성할 때 개념만 취했다고 판단했으나, 검수에서 원문의 문장·예시·수치를 우리말로 옮긴 대목이 다수 확인됐다. 이후 해당 대목을 우리 맥락의 문장과 예시로 다시 썼지만, 규칙의 **선택과 구성**은 여전히 원자료에 기대고 있다. 따라서 "개념만 취했으므로 고지 의무가 없다"고 주장하지 않고, 위 고지를 싣는 쪽을 택했다. MIT는 고지와 라이선스 전문을 함께 두면 재배포·수정·내부 배포를 모두 허용한다 — 고지를 다는 편이 판정에 시간을 쓰는 것보다 싸고 확실하다.

라이선스 전문은 `LICENSE-academic-pptx.txt`로 이 디렉터리에 함께 둔다.

### 1-b. academic-pptx의 라이선스 표기 충돌 (기록)

저장소 `LICENSE.txt`는 MIT 전문이고 명의는 `Copyright (c) 2026 Gabberflast`인데, 같은 저장소 `SKILL.md` frontmatter는 `license: Proprietary. LICENSE.txt has complete terms`로 적혀 있다. 우리는 **LICENSE 파일을 우선**해 MIT로 본다. 저자의 표기 오류로 **추정**하나 확정은 아니다 — letta 건(§2)과 같은 유형의 불일치이므로 한쪽만 침묵하지 않고 여기 남긴다.

## 2. `letta` 헬퍼 — 코드 사용 금지 판정

같은 저장소 안에서 저작권 표시가 **어긋난다**(2026-07-26 직접 확인 — 세 갈래 · 2026-11-16 커밋 `6785511e7d39` 에서 LICENSE 와 파일 머리만 다시 확인):

| 위치 | 2026-07-26 표시 | 2026-11-16 표시 |
|---|---|---|
| PPT 헬퍼 소스 9개 파일 전부, 파일 머리 | `Copyright (c) OpenAI. All rights reserved.` | 같음 |
| 저장소 라이선스 파일 | `LICENSE.txt` 부록(APPENDIX) 189행 `Copyright (c) Microsoft Corporation.` | `LICENSE`(27행) = MIT 전문 · `Copyright (c) 2026 Letta, Inc.` · Microsoft 부록 줄 없음 |
| GitHub이 판정한 저장소 라이선스 | `NOASSERTION` (자동 인식 실패) | 미검증(GitHub API 를 받지 못함) |

`All rights reserved.`는 그 자체로 **재사용 허가가 없다는 선언**이다. 파일 머리의 권리자와 LICENSE 의 권리자가 다르고(2026-07-26 에는 Microsoft 부록 · 2026-11-16 에는 Letta MIT), 2026-07-26 에는 플랫폼조차 라이선스를 특정하지 못했다. 저장소 LICENSE 가 MIT 로 바뀌어도 파일 머리의 OpenAI `All rights reserved.` 표시는 그대로라, 이 상태에서 코드를 가져오면 어느 조건을 지켜야 하는지조차 확정할 수 없다.

**판정: 코드·문자열·구조를 일절 가져오지 않는다. 동작 명세(무엇을 검사하는가) 수준의 참고만 한다.**

배포 범위가 내부·지인으로 좁아도 판정은 같다. 저작권은 배포 규모가 아니라 복제·배포 행위 자체에 걸리고, 내부 배포도 명백한 배포다. 원 저작자가 문제 삼지 않을 가능성과 권리가 없다는 사실은 별개다.

### 자체 구현 시 지킨 규칙
1. **구현 로직은 읽지 않는다.** 열람 범위는 라이선스 판정에 필요한 최소한 — 9개 파일의 **머리 부분(저작권 표시)**, export 목록, 경고 출력 형식, 함수 이름에 한정했다. 구현 착수 이후에는 **재열람하지 않는다**. (§2 표의 저작권 문구는 이 범위에서 확인한 것이다.)
2. 임계값·판정 로직·파일 구조·함수명·메시지 문구를 **우리 요구에서 새로 도출**한다.
3. 실제 자료로 측정해 임계값을 정한다(아래 §3).

부수 효과로, 원본이 요구하는 네이티브 렌더링 의존성 없이 **Pillow만으로 동작**하고, 우리 규칙(의도적 예외 표시, 여백 비율 판정)을 넣을 수 있게 됐다.

### 시험 자체가 틀렸던 것 네 건
같은 유형이 네 번 나왔다 — **통과하고 있었지만 아무것도 검증하지 않던 시험**이다. 픽스처가 초록불이라는 것은 검사가 작동한다는 증거가 아니다.

- 단정이 결함 **개수**만 보고 있었다. 변이 시험에서 심각도·임계값을 바꾼 17가지 중 14가지가 그대로 통과했다 — FAIL/WARN 구분은 문서가 한 절을 할애한 계약인데 픽스처가 하나도 고정하지 않고 있었다. `규칙:심각도`를 단정하도록 바꾸자 같은 변이가 6건 실패로 잡힌다.

- `fullBleed` 면제 시험이 요소를 캔버스 경계에 **정확히 맞춰** 두어, 면제가 없어도 통과했다. 면제 경로는 확인된 적이 없었다. 경계를 넘는 요소로 다시 시험했다.
- 잘림 픽스처가 글자를 **폭 28~90px 덩어리**로 그려 실제 글자와 닮지 않았다. 판정을 구간 길이 기준으로 바꾸자 이 픽스처가 띠로 읽혀 통과했다. 글자 획 크기(3~7px)로 다시 그렸다.
- 잘림 픽스처가 **오른쪽과 아래쪽을 한 장에** 담고 있었다. 아래쪽 블록만으로 통과했고 오른쪽 경로는 줄곧 0점을 내고 있었다(실측: 아래쪽 151 vs 오른쪽 **0**). 오른쪽만 자른 픽스처를 따로 뒀다.

그래서 두 픽스처 모두 **결함 케이스와 정상 케이스를 함께** 담는다. 검출 건수만 세면 임계값을 조이는 쪽으로 기울고, 위와 같은 빈 통과는 눈에 띄지 않는다.


### 임계값을 바꿨을 때 다시 확인하는 법

역테스트가 두 벌 있다. 도구를 손대면 **둘 다** 돌린다.

```
# 게이트1 — 검출 23종 + 정상·면제 23종 · pptxgenjs 는 실행 위치(작업 디렉터리)에서 찾는다
(cd deck && npm install && node ../tools/negtest/lint_cases.js)   # 48/48 — 패키지 저장소(deck/node_modules 는 git 제외)

# 게이트2 — 결함 5종 + 정상 3종 + 판정 불가 2종
python tools/negtest/make_negtest.py                       # png/ 10장 생성 + 기대 판정 출력 + 경로 통합 3종
python tools/qa_slides.py --png-dir tools/negtest/png --out negtest_qa.md
```

역테스트 두 벌은 **패키지 저장소에서만** 돈다 — 배포 패키지에는 `tools/negtest/` 가 없다(개발·검증 하네스라 `tools/build_packages.sh` 가 뺀다). 설치본만 있는 PC 에서 도구를 고쳤으면 패키지 저장소에서 위 명령으로 돌린다(pptxgenjs 가 없는 작업 폴더에서 돌리면 `lint_cases.js` 는 종료 2). `negtest_qa.md`의 판정이 `make_negtest.py`의 `EXPECTED`와 10/10 일치해야 한다 — `make_negtest.py` 자체는 경로 통합 3/3 을 함께 검사한다. 하나라도 어긋나면 임계값 변경이 검출 능력을 깎은 것이다.

두 픽스처 모두 **검출 케이스만 담지 않는다.** 검출력만 세면 임계값을 조이는 쪽으로 기울기 때문에, 걸리면 안 되는 정상 케이스(full-bleed rail, 옅은 카드, 어두운 표지, 배경 카드 위 텍스트, 각종 면제)를 같은 비중으로 넣었다. 게이트2에는 **판정 불가가 정답인 케이스** 2종(그라데이션·반분할)도 있다 — 이것들은 `WARN:bg-unclear`가 나와야 정상이다.

|---|---|---|---|---|
| pptxgenjs | **4.0.1** | MIT | PPTX 생성 | 아니오(사용자가 npm 설치) |

| Poppler (`pdftoppm`) | 24.02.0 | GPL-2 또는 GPL-3 | 렌더 · 클라우드 경로(Windows 밖) · PDF→PNG 래스터(있으면 우선) | 아니오(시스템 패키지) |

| Microsoft PowerPoint | — | 상용 | 렌더 · COM · 로컬 Windows PC 기본 · 최종 | 아니오(사용자 보유분) |

**pptxgenjs 버전을 적어 두는 이유**: `pptx_lint.js`는 슬라이드 객체의 내부 배열(`_slideObjects` 등)을 직접 읽는다. 이는 공개 API가 아니므로 상위 버전에서 구조가 바뀌면 요소를 하나도 못 찾을 수 있다. 그 경우 **"결함 0"으로 조용히 통과하지 않고 표준 오류로 경고**하도록 해 뒀지만, 버전을 올렸다면 패키지 저장소에서 `tools/negtest/lint_cases.js`를 pptxgenjs 가 설치된 폴더에서 돌려(§3 「임계값을 바꿨을 때 다시 확인하는 법」) 48/48이 나오는지 먼저 확인한다.

라이브러리를 번들하지 않으므로 이들의 재배포 조건은 발생하지 않는다. 렌더 엔진은 **환경이 정한다** — 로컬 Windows PC 는 PowerPoint(COM · 모든 로컬 Windows PC 에서 쓸 수 있다고 전제 · 최종), 클라우드(리눅스 컨테이너)와 Windows 밖 로컬 PC(Mac·Linux)는 LibreOffice(Impress 부품) → PDF → 래스터(근사 · 확정은 Windows COM · 근사로 끝낸 덱의 끝 상태 = `qa_procedure.md` §완료 선언 조건 「클라우드 끝 상태」). Windows 에서 COM 이 안 되면 전제 위반으로, 클라우드·Windows 밖 로컬 PC 에서 LibreOffice 부품을 설치할 수 없으면 그 사유로 게이트 2·3을 **미실행으로 기록**한다(→ `qa_procedure.md` §2-1 렌더).
