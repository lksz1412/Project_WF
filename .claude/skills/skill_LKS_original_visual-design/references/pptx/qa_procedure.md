# 검증 절차 (3-게이트)

`pptx.md`(PPTX 어댑터)가 **4단계(게이트1 호출 형식)와 5~7단계(실행·완료 조건)**, 그리고 **도구를 고쳤을 때**(§게이트 1 「도구를 고쳤을 때」) 읽으라고 지시하는 문서다.

아래 명령의 `<설치경로>`는 도구 폴더 `tools/` 의 부모를 펼친 절대 경로다(설치본·패키지 저장소 값의 원본 = `SKILL.md` 「도구 경로」 · `~` 는 쓰지 않는다). 작업 폴더는 어디든 되므로 도구는 **절대 경로로** 부른다.

## 왜 3개인가 — 게이트별로 잡히는 결함이 다르다

한 가지 방법으로는 전부 잡히지 않는다. 잡히는 결함과 못 잡는 결함이 게이트마다 다르므로, **결함 종류를 보고 담당 게이트를 정한다.**

| 결함 | 게이트 1 (좌표) | 게이트 2 (픽셀) | 게이트 3 (눈) |
|---|:---:|:---:|:---:|
| 요소가 캔버스 밖으로 나감 | **탐지** | 잘림만 간접 | 보임 |
| 텍스트끼리 겹침 | **탐지** | 못 잡음 | 보임 |
| **텍스트가 자기 상자를 넘침** (캔버스 안) | **탐지**(기본 WARN · `overflowFail`로 FAIL 승격) — 글자수·크기로 높이 추정 | **원리상 불가** | 보임 — 최종 확정 |
| 표 셀 **단어 중간 끊김** (공백 없는 토큰 > 열 폭) | **탐지**(FAIL · 한계 근처는 WARN 빠듯함) — 토큰 폭 추정 | 못 잡음 | 보임 — 경계선 근처 확정 |
| 빈 슬라이드 / 렌더 실패 | 못 잡음 | **탐지** | 보임 |
| 내용 과밀 | 못 잡음 | **탐지**(잉크 비율) | 보임 |
| 안전 여백 침범 | 못 잡음 | **탐지** | 보임 |
| 폰트 미설치 → 치환 | 못 잡음 | **탐지**(.pptx 대조) | 치환된 줄 알기 어려움 |
| 제목이 주제 라벨 | 못 잡음 | 못 잡음 | **탐지** |
| 레이아웃 단조·리듬 붕괴 | 못 잡음 | 못 잡음 | **탐지** |
| 색·정렬 불일치 | 못 잡음 | 부분 | **탐지** |

**"텍스트 상자 넘침"은 픽셀 검사로 잡을 수 없다.** 넘친 글자도 캔버스 안에 있으면 정상 픽셀과 구분되지 않는다. 게이트 1이 글자수·글자크기·상자 폭으로 필요한 높이를 **추정**해 잡고, 게이트 3이 눈으로 확정한다. 게이트 2에 기대하지 않는다.

추정이므로 **기본 판정은 WARN**이고, 상자 높이의 1.25배를 넘을 때만 보고한다. 폰트마다 실제 글자 폭이 다르므로 경계선 근처는 잡히지 않는다 — 게이트 3을 건너뛰면 안 되는 이유다.

**단, 넘침을 반드시 막아야 하는 산출물(카드형·표형처럼 상자 높이가 빠듯한 덱)에서는 `reportSlide(slide, n, undefined, { overflowFail: true, slack: 1.05 })`로 호출한다** — 넘침을 WARN이 아니라 **FAIL**로 승격하고(빌드 중단), 여유를 5%로 조인다. 기본값(WARN + 1.25배 여유)은 "상자에 꽉 참"까지 정상으로 흘려보내므로, 게이트1만 믿으면 실제 넘침이 통과한다. **검증된 슬라이드 사이에 새로 끼운 슬라이드의 문구가 길어 넘쳤는데 게이트1이 WARN으로 통과시켜 그대로 배포된 실사고가 있었다** — 그래서 넘침이 치명적인 덱은 `overflowFail`로 잡고, 폰트 추정 오차만 게이트 3(눈)이 확정한다.

**넘침 검사가 실효를 갖는 대상은 높이를 고정한 상자(`note`·`caption`·수동 `addText` 등)뿐이다.** 두 경우는 구조적으로 빠진다: (1) **높이를 내용에 맞춰 자동 산정하는 카드**(글자수로 상자 높이를 정하는 헬퍼)는 검사기와 같은 폭·폰트 모델로 높이를 잡으므로 필요높이/상자높이 비율이 1을 넘지 못한다 — 이런 카드의 과밀은 넘침이 아니라 **아래 요소를 밀어내는 바닥선 침범**으로 나타나며, 그건 레이아웃 자리표시자(`claimBelow` 류)가 잡는다. (2) **`addTable`이 만든 표는 `checkOverflow` 대상이 아니다**(행이 `text` 필드를 갖지 않는다) — 표 셀이 2줄로 접히는 것은 게이트1이 못 보고 게이트3(육안)로만 확정된다. **텍스트 상자에서 표로 재설계하면 넘침 검사 밖으로 나가는 것**임을 유념한다. 표에서 게이트1이 보는 것은 **단어 중간 끊김** 하나다(`checkTableWordBreak` · 아래 판정 범위).

## 게이트 1 — 정적 린트 (렌더 전, 비용 0)

`tools/pptx_lint.js`. 의존성 없음(Node 표준만).

생성 스크립트에서 슬라이드에 요소를 다 넣은 직후, **`writeFile()` 전에** 호출한다.

`require`를 쓰는 CommonJS 스크립트에서는 최상위에 `await`를 쓸 수 없다. 아래처럼 `main()`으로 감싼다.

```js
const path = require("path");
const os = require("os");
const PptxGenJS = require("pptxgenjs");
// 설치본 = 홈의 .claude(아래 그대로) · 패키지 저장소에서 부르면 이 값을 그 저장소의 절대 경로로 바꾼다
const TOOL_ROOT = path.join(os.homedir(), ".claude");
const { reportSlide, lintSummary } = require(path.join(TOOL_ROOT, "tools", "pptx_lint.js"));

async function main() {
  const pptx = new PptxGenJS();
  pptx.defineLayout({ name: "W16x9", width: 13.333, height: 7.5 });
  pptx.layout = "W16x9";

  let dirty = false;

  const slide = pptx.addSlide();
  slide.addText("제목", { x: 0.6, y: 0.5, w: 12.1, h: 1.0, fontSize: 34 });
  slide.addText("본문", { x: 0.6, y: 1.8, w: 5.8, h: 3.2, fontSize: 27 });
  dirty = reportSlide(slide, 1, undefined, { overflowFail: true, slack: 1.05 }) || dirty;   // 넘침도 FAIL로

  // …모든 슬라이드에 대해 같은 방식으로

  // 마지막에 집계를 한 줄 남긴다. 통과했을 때 아무 출력이 없으면
  // "깨끗함"과 "린트를 안 불렀음"이 구분되지 않는다.
  if (lintSummary() || dirty) { console.error("게이트1 결함 — 생성 중단"); process.exit(1); }
  await pptx.writeFile({ fileName: "out/deck.pptx" });
}

main().catch((e) => { console.error(e); process.exit(1); });
```

| 함수 | 시그니처 | 반환 | 쓰는 때 |
|---|---|---|---|
| `reportSlide` | `(slide, slideNo, dims?, opts?)` | `true`면 결함 있음 | 기본. 콘솔에 상세 출력까지 한다 |
| `lintSlide` | `(slide, dims?, opts?)` | 결함 객체 배열 | 결과를 직접 다루고 싶을 때 |
| `checkBounds` · `checkOverlaps` · `checkOverflow` · `checkTableWordBreak` | `(slide, dims?, opts?)` | 결함 객체 배열 | 특정 검사만 돌릴 때 |
| `lintSummary` | `()` | FAIL이 있으면 `true` | 마지막에 1회. `슬라이드 N장 검사 · FAIL n · WARN n`을 출력한다 |

**`opts` 필드**(넷째 인자): `overflowFail:true` → 상자 넘침을 WARN이 아니라 **FAIL**로 승격(빌드 중단). `slack`(기본 1.25) → 넘침 판정 여유 배수, 빽빽한 덱은 1.05로 조인다. `failOn`(기본 `["FAIL"]`) → 차단으로 볼 severity 목록. 넘침이 치명적인 덱은 `{ overflowFail: true, slack: 1.05 }`가 표준이다.

`lintSummary()`는 `reportSlide()`가 **한 번도 불리지 않았으면** 그 사실을 오류로 알린다. 게이트1을 통째로 빠뜨린 채 "결함 0"으로 넘어가는 것을 막는 장치다.

- 첫 인자는 **pptxgenjs 슬라이드 객체**다(요소 배열이 아니다). 내부 요소 배열은 도구가 알아서 찾는다.
- 결함 객체: `{rule, severity, index, kind, detail, suggestion}`. `detail`에 실제 수치가, `suggestion`에 수정 방향이 들어 있다.
- 캔버스 기본값은 **13.333″×7.5″**. 다르면 `dims`로 `{ w: 10, h: 5.625 }`를 넘긴다 — `reportSlide`는 **3번째**, 나머지 함수는 **2번째** 인자다.

### 심각도 — `reportSlide`는 FAIL에서만 `true`
| 심각도 | 규칙 | 뜻 |
|---|---|---|
| **FAIL** | `bounds` · `overlap` · `wordbreak`(가용폭 초과) | 좌표로 확정되는 결함(`bounds`·`overlap`) · 추정 폭이 가용 폭을 넘는 표 셀 토큰(`wordbreak` — 단어 중간 끊김은 읽는 사람이 되돌릴 수 없어 추정이어도 막는다). 생성을 멈춘다 |
| **WARN** | `overflow` · `unchecked` · `wordbreak`(빠듯함) | 추정이거나 검사 못 한 것. 출력하되 막지 않는다 |

넘침은 글자 폭을 추정해 재는 값이라 확정이 아니다. 이것까지 생성을 막으면 추정치가 하드 게이트가 되어 심각도를 나눈 의미가 사라진다. 표 셀 끊김(`wordbreak` FAIL)만은 추정이어도 막는다 — 경계 근처라 거짓 FAIL 이 의심되면 그 셀 `options` 에 `wordbreakOk: true` 와 사유 주석을 달아 생성한 뒤 렌더로 확정하고(확정 = Windows PowerPoint COM 렌더 — 클라우드 근사 렌더로는 확정하지 않는다), 한 줄에 들어가면 유지 · 끊기면 표시를 빼고 열 폭을 고친다. **경고도 막고 싶으면** `reportSlide(slide, n, undefined, { failOn: ["FAIL", "WARN"] })`.

WARN이라고 넘기라는 뜻은 아니다 — 완료 조건은 **WARN 전부 처리 또는 근거 기재**다.

### 판정 범위
- 겹침 판정 대상은 **글자가 실제로 들어 있는 요소끼리**다. 배경 카드(도형) 위의 글자는 정상이므로 결함이 아니다. 겹침 최소 면적 0.01 in².
- **표는 좌표 단위가 다르다.** pptxgenjs는 표만 EMU(914400 = 1인치)로 저장하므로 도구가 환산해 판정한다. `h` 없이 `rowH`만 준 표는 `rowH × 행수`로 높이를 채운다.
- `x: "50%"` 같은 백분율은 캔버스 크기로 환산해 판정한다.
- 좌표를 끝내 계산할 수 없는 요소는 `unchecked` WARN으로 남는다. **"결함 0"과 "검사 못 함"을 구분하기 위해서다** — 조용히 넘기면 검사한 줄 알게 된다. 없애려면 크기를 숫자로 명시한다.
- **표 셀은 단어 중간 끊김만 본다**(`wordbreak`). 셀의 공백 없는 가장 긴 토큰 폭(넘침 검사와 같은 전각 1.0·반각 0.5 추정 · run 경계는 끊는 자리가 아니다)이 열 폭 − 좌우 셀 여백(셀 `margin` → 표 `margin` → pptxgenjs 기본 0.1″ 씩)을 넘으면 FAIL이다. 병합 셀(colspan)은 병합한 열 폭의 합으로 보고, 위 행의 rowspan 이 내려온 칸은 건너뛰어 열을 센다. 여러 줄 감김은 결함이 아니다(행 높이만 는다). 보고에는 셀 위치(1부터 센 행·열 — 머리글 행 포함)·토큰·필요폭·가용폭이 찍힌다. 열 폭(`colW`·`w`)을 알 수 없는 표는 `unchecked` WARN.
- **표 셀 빠듯함**: FAIL 은 아니나 그 토큰의 추정 폭이 가용 폭의 **80%**를 넘으면 `wordbreak` **WARN**이다. 폭 추정은 글자에 따라 실제보다 좁게 나와(대문자·숫자 위주가 심하다) 이 대역에서는 FAIL 을 놓칠 수 있다. 80% 는 실제 폭이 추정의 1.25배까지 넓어도 잡는 선이고, 대문자 위주 토큰은 그보다 더 어긋날 수 있다. **WARN 은 Windows PowerPoint 렌더로 확정한다.**

**FAIL 결함이 있으면 PPTX를 만들지 말고 멈춘다.** WARN은 위 severity 계약대로 생성 자체를 막지 않지만, 완료 전에는 모두 처리하거나 유지 근거를 기록한다.

### 의도적 예외 표시
| 표시 | 뜻 |
|---|---|
| `fullBleed: true` | 캔버스 가장자리까지 의도적으로 채우는 요소(표지 배경, 상단 띠) → 경계 검사 면제 |
| `overlapOk: true` | 겹침이 디자인인 요소(뱃지, 강조 오버레이) → 겹침 검사 면제 |
| `overflowOk: true` | 넘침을 알고 두는 요소 → 넘침 검사 면제 |
| `wordbreakOk: true` | 단어가 끊겨도 되는 표 셀(좁은 칸의 긴 URL 등) → 표 셀 끊김 검사(빠듯함 포함) 면제. 표 옵션에 달면 표 전체, 셀 하나만이면 그 셀의 옵션에 단다(`{ text: "…", options: { wordbreakOk: true } }` — pptxgenjs 셀은 자기 옵션을 `options` 에 둔다) |

표시는 **옵션 객체의 최상위 키**로 넣는다. `options: { ... }`로 한 겹 더 감싸면 도구가 찾지 못해 면제가 조용히 무시된다.

```js
// 상단 띠 — 캔버스 밖까지 의도적으로 빼서 여백 없이 채운다
slide.addShape(pptx.ShapeType.rect, {
  x: -0.1, y: 0, w: 13.6, h: 1.2, fill: { color: BRAND }, fullBleed: true,
});
```

**표시 없는 위반만 결함이다.** 반대로, 결함을 없애려고 아무 데나 표시를 붙이면 게이트가 무력해진다. 표시할 때는 이유를 코드 주석으로 한 줄 남긴다.

### 도구를 고쳤을 때
`tools/negtest/lint_cases.js`가 **48종**(검출 24 + 정상·면제 24)을 검사한다. 각 케이스는 결함 **개수**가 아니라 `규칙:심각도`를 단정한다 — 개수만 세면 심각도를 바꿔도 통과한다. `pptx_lint.js`를 손대면 반드시 돌린다.

```
node <설치경로>/tools/negtest/lint_cases.js     # 48/48 이어야 한다 · <설치경로> = 패키지 저장소(설치본에는 tools/negtest/ 가 없다 — ATTRIBUTION.md §3)
```
pptxgenjs는 **현재 작업 디렉터리** 기준으로 찾는다. 없으면 그 디렉터리에서 `npm install pptxgenjs`.

역테스트는 **두 벌**이다 — 위 게이트 1(`lint_cases.js`)과 게이트 2(`make_negtest.py` 가 픽스처 10장을 만들고 `qa_slides.py` 판정이 그 `EXPECTED` 와 10/10 일치 · 경로 통합 3/3). `pptx_lint.js`·`qa_slides.py`(판정 규칙·임계값 포함) 어느 쪽을 손대도 **둘 다** 돌린다. 게이트 2 역테스트의 명령·기대 판정은 `ATTRIBUTION.md` §3 「임계값을 바꿨을 때 다시 확인하는 법」이 원본이다 — 하나라도 어긋나면 그 변경이 검출 능력을 깎은 것이다.

## 게이트 2 — 기계 검사 (렌더 후)

### 2-1. 렌더
**렌더 엔진 = 환경 고정.** 설치된 엔진을 탐지해 고르지 않는다. 어느 엔진으로 렌더했는지 결과에 기록한다.

| 환경 | 렌더 엔진 | 판정 지위 |
|---|---|---|
| **로컬 Windows PC** | PowerPoint COM(`tools/render_pptx.ps1`) — 모든 로컬 Windows PC 에서 쓸 수 있다고 전제 · `soffice` 가 깔려 있어도 쓰지 않는다 | 최종(실제 PowerPoint 가 그린 결과 · 서체 대체 없음) |
| **클라우드(리눅스 컨테이너)** | LibreOffice(Impress 부품) → PDF → 래스터(`pdftoppm` 이 있으면 그것 · 없으면 pypdfium2) | 근사 미리보기(서체 대체로 줄바꿈 근사) — 확정은 Windows COM |
| **Windows 밖 로컬 PC**(Mac·Linux — PowerPoint COM 없음) | 클라우드 행과 같은 경로(아래 「클라우드 경로」 명령 · `soffice` 가 PATH 에 있어야 함) | 클라우드 행과 같음 |

**COM 경로** — `tools/render_pptx.ps1`(PowerPoint COM):

```powershell
powershell -ExecutionPolicy Bypass -File <설치경로>/tools/render_pptx.ps1 `
  -Pptx out/deck.pptx -OutDir out/render -Width 1920
```

- 출력: `out/render/png/slide-001.png …` + `out/render/deck.pdf`(`-NoPdf`로 생략).
- PowerPoint의 내보내기 파일명은 **언어 설정에 따라 달라진다**(한국어 환경은 `슬라이드1.PNG`). 스크립트가 끝자리 숫자로 정렬해 `slide-NNN.png`로 통일하므로 이후 도구는 언어 환경과 무관하다.
- `png=` 개수와 `slides=` 개수가 다르면 경고 + 종료코드 1. 이때는 렌더 자체가 실패한 것이므로 검사로 넘어가지 않는다.
- 스크립트가 **내보내기 직전에** `png/`의 기존 PNG를 지운다. 이전 렌더가 더 길었으면 남은 파일이 새 결과와 뒤섞여 슬라이드 번호가 밀린다. 지우는 시점을 내보내기 직전으로 둔 이유는, 앞서 지워 놓고 렌더가 실패하면 멀쩡한 이전 결과까지 잃기 때문이다.
- 슬라이드가 0장이면 렌더하지 않고 종료코드 1로 끝난다.
- PowerPoint가 이미 실행 중이면 그 인스턴스에 붙고 **끝낼 때 종료시키지 않는다**(사용자가 열어 둔 문서를 닫지 않기 위해서).

**클라우드 경로** — 리눅스 컨테이너·Windows 밖 로컬 PC(LibreOffice Impress 부품 → PDF → 래스터). **작업 폴더 루트에서**, 블록 전체를 **한 번의 명령 실행(한 셸)으로** 돌린다 — `R` 은 셸 변수라 줄을 끊어 따로 실행하면 비어서 PDF 가 작업 폴더 루트에 써지고 래스터 줄이 실패한다:

```bash
R=out/render/$(date +%Y%m%d-%H%M%S) && mkdir -p "$R/png"
soffice --headless --norestore --convert-to pdf --outdir "$R" out/deck.pptx
# 래스터 — pdftoppm(Poppler)이 있으면 그것, 없으면 pypdfium2(같은 파일 이름 규칙)
if command -v pdftoppm >/dev/null; then pdftoppm -png -r 144 "$R/deck.pdf" "$R/png/slide"; else R="$R" python3 -c "import os,pypdfium2 as p; r=os.environ['R']; d=p.PdfDocument(r+'/deck.pdf'); w=len(str(len(d))); [d[i].render(scale=144/72).to_pil().save(f'{r}/png/slide-{i+1:0{w}d}.png') for i in range(len(d))]"; fi
echo "$R"
```

- 출력: `<폴더>/png/slide-NN.png`(자릿수 = 장 수의 자릿수 · 두 래스터 도구 같음) + `<폴더>/deck.pdf` — `<폴더>` = 렌더마다 새로 만드는 시각 이름 폴더(`out/render/<시각>/` · 블록 마지막 줄이 찍는다). 게이트 2·3 명령의 `out/render` 자리에는 **찍힌 폴더 경로**를 그대로 적는다 — `--png-dir <폴더>/png` · 게이트 3 몽타주 `--out <폴더>/montage.png`(`$R` 는 셸이 바뀌면 비어 있다). 파일명 끝자리 숫자로 정렬하므로 `qa_slides.py`·`montage.py` 는 그대로 쓴다.
- 144dpi = 13.333″ 캔버스에서 폭 1920px — COM 경로의 `-Width 1920` 과 같아 게이트 2 `--margin-px` 기본값(72px = 0.5″)이 그대로 맞는다.
- **지난 결과를 지우지 않는다** — 렌더마다 새 폴더에 쓰므로 옛 `deck.pdf` 를 새 렌더로 잘못 읽을 일이 없고(변환이 실패하면 새 폴더에 `deck.pdf` 가 없다), 수정 전후 비교에도 그대로 쓴다. 정리는 작업이 모두 끝난 뒤 한 번에 한다(삭제마다 승인 창이 떠 연속 작업이 끊긴다 — `memory:feedback_flow_interruption` 원칙 4). 장 수 대조는 게이트 2 의 `--pptx` 가 한다(python-pptx 필요 · 없으면 미실행으로 드러남 · 다르면 FAIL).
- 서체 대체가 일어나므로 줄바꿈·넘침 판정은 참고용으로만 보고, 확정은 COM 렌더로 한다.
- 게이트 2 폰트 검사(`qa_slides.py --pptx`)는 Windows 레지스트리에서 설치 폰트를 읽으므로 클라우드에서는 **미실행**으로 남고 종료코드가 1이다 — 서체 확인도 Windows COM 렌더 몫이다.
- 변환 자체의 사실(필요한 부품 등)은 `skill:skill_LKS_custom_document` `references/pptx/GUIDE.md` 「Converting to Images」 가 원본이다.

#### 렌더를 못 하는 경우
- **Windows PC 에서 COM 이 안 된다** — 전제 위반이다. 게이트 2·3 을 **미실행**으로 기록하고 사용자에게 알린다. LibreOffice 로 대체하지 않는다.
- **클라우드·Windows 밖 로컬 PC 에 LibreOffice 부품이 없다** — 설치한다(리눅스 = `sudo apt-get install -y libreoffice-impress`). 설치할 수 없으면 게이트 2·3 을 **미실행**으로 기록한다.

어느 쪽이든 게이트 1만 통과한 상태이므로 **"부분 완료 — 게이트 2·3 미실행(사유)"**으로 기록한다.

건너뛴 게이트를 통과로 적지 않는다. 이것은 표기 문제가 아니라, 그 상태로 배포하면 아무도 확인하지 않은 덱이 나간다는 뜻이다.

### 2-2. 검사
`tools/qa_slides.py` — Pillow 필요, 폰트 검사·장 수 대조에 python-pptx 필요(없으면 둘 다 **미실행**).

```powershell
python <설치경로>/tools/qa_slides.py --png-dir out/render/png --pptx out/deck.pptx --out out/qa_report.md
```

| 검사 | 측정값 | 임계 | 판정 |
|---|---|---|---|
| 빈 슬라이드 | 슬라이드 전체가 사실상 한 색 | — | **FAIL**(`--allow-blank` 로 적은 장은 `빈칸(의도)`) |
| 배경 판정 불가 | 여백 링에서 으뜸 색이 차지하는 비율 | < 0.70 | WARN — **여백 침범·과밀을 건너뛴다** |
| 여백 침범 | `margin share` (잉크 중 안전여백 안 비율) | > 20% | WARN |
| 과밀 | `content%` (배경과 **뚜렷이** 다른 픽셀) | > 35% | WARN |
| 가장자리 잘림 | 최외곽 선의 **끊긴 잉크 덩어리** 수 | > 2 + 잉크 있음 | WARN |
| 읽을 수 없는 파일 | 이미지 열기 실패 | — | **FAIL** |
| 장수 불일치 | 덱 장수 ↔ PNG 장수 (`--pptx` 필요 · python-pptx 없으면 미실행) | 다름 | **FAIL** |
| 폰트 미설치 | .pptx 사용 폰트 ↔ 시스템 설치 폰트 | 하나라도 없음 | **FAIL** |

보고서에 `ink%`와 `content%`가 **따로** 나온다. 둘의 역할이 다르다.
- `ink%` = 배경과 채널당 12 넘게 다른 픽셀. 옅은 카드도 포함되므로 **빈 슬라이드 판정**에 쓴다.
- `content%` = 배경과 채널당 64 넘게 다른 픽셀. 옅은 카드는 빠지고 글자·진한 면만 남으므로 **과밀 판정**에 쓴다. 카드를 깔았다고 과밀로 잡히지 않는다.

판정 규칙은 전부 실측으로 정해졌다(근거 = `ATTRIBUTION.md` §3). 그대로 두는 편이 좋다 — 바꾸면 §게이트 1 「도구를 고쳤을 때」의 역테스트 두 벌을 돌린다.

- **배경색**은 안전여백 링의 으뜸 색으로 본다. 다만 **그 색이 링의 70%를 넘지 못하면 배경을 정할 수 없다고 보고 판정을 멈춘다**(`WARN:bg-unclear`). 슬라이드가 큰 띠로 반씩 나뉘어 있으면 어느 쪽을 배경이라 부를 근거가 없고, 그 상태에서 낸 비율은 전부 뜻이 없기 때문이다. 실측 경향: 보통 슬라이드는 0.9 이상 · rail 있는 구성은 0.78 안팎 · 전면 표지 1.0 vs 반분할 0.5 안팎 · 그라데이션은 0에 가깝다.
  - 그라데이션·사진 배경도 여기 걸린다. 단일 배경색이 아예 없으므로 정상이며, **이런 슬라이드는 게이트3에서 눈으로 판정한다.**
- **여백 침범**은 절대 픽셀 수가 아니라 **비율**이며, 균일한 full-bleed 띠는 세지 않는다. 꼬리말·상단 띠는 원래 여백에 있으므로 절대 개수로 재면 전 슬라이드가 걸린다(실측 확인). 여백이 화면 절반을 넘게 차지하는 작은 이미지에서는 이 검사를 건너뛴다.
- **가장자리 잘림**은 **"잉크 덩어리가 몇 개로 끊겨 있는가"**로 본다. 의도한 띠는 굵기와 무관하게 **한 덩어리**이고, 잘린 글자는 글자마다·글줄마다 덩어리가 생긴다. 구간 길이로 재던 이전 방식은 세로 가장자리에서 무력했다 — 좌·우 가장자리의 교대 주기는 글자 폭이 아니라 **줄 높이**여서, 오른쪽으로 흘러넘친 글자가 0점을 받았다.
- **빈 슬라이드**는 배경색을 몰라도 판정한다 — "내용이 없다"는 색이 무엇이냐가 아니라 **변화가 있느냐**의 문제다. 배경 신뢰도 뒤에 묶어 두었더니 질감·그라데이션 배경에서 게이트2의 유일한 FAIL 급 검사가 통째로 꺼지고 종료코드 0이 나갔다.

폰트 검사는 **여섯 가지 상태**를 구분해 적는다. 첫 번째를 뺀 나머지는 통과가 아니라 미실행이다.

| 상태 | 보고 |
|---|---|
| 정상 비교 완료 | `missing: none` 또는 `missing (FAIL): …` |
| python-pptx 미설치 | **미실행** — 설치 안내 |
| 폰트 검사 중 오류 | **미실행** — 오류 종류를 적는다. 보고서는 그대로 생성된다 |
| `.pptx` 를 열 수 없음(없거나 손상) | **미실행** — 파일 문제를 그대로 적는다 |
| 런 단위 폰트명 없음(테마 상속) | **미실행 [근거 미발견]** — 서체를 명시 지정해 해소 |
| 설치 폰트 목록을 못 읽음 | **미실행** — 목록이 비었다고 전건 FAIL로 처리하지 않는다 |

폰트 이름은 **한글 표시명도 인식한다**. 한글 PowerPoint에서 서체를 고르면 파일에는 `맑은 고딕`이 들어가는데 레지스트리에는 영문명만 있다. 레지스트리로 못 찾은 이름만 폰트 파일 안의 이름표를 읽어 대조하므로, 한글 이름을 썼다고 FAIL이 나지 않는다. 라틴·동아시아·복합문자 서체(`a:latin`·`a:ea`·`a:cs`)를 모두 수집한다 — 라틴만 보면 한글이 전부 치환되는데도 "missing: none"이 나온다.

기타
- 파일 하나를 열지 못해도 **나머지는 계속 검사**하고 그 줄만 `FAIL:unreadable`로 남긴다. 중간에 멈추면 이전 실행의 보고서가 그대로 남아 최신 결과로 오독된다.
- 알려진 예외는 `--except-slides 1,2`로 지정한다(여백·가장자리 검사가 함께 면제된다). **보고서에 이유를 남긴다.**
  예외 자격은 **게이트3에서 눈으로 판정하기로 한 슬라이드**(그라데이션·사진 배경 등)에 한한다. 경고를 없애려고 붙이면 게이트가 무력해진다 — 게이트1의 예외 표시와 같은 규율이다.
- 의도한 빈칸(백지) 장(`pptx.md` 「선택 패턴」)은 `--allow-blank 12,30`으로 장 번호를 적는다. 그 장은 `FAIL:blank` 대신 `빈칸(의도)`로 보고되고 FAIL 로 세지 않는다. 적지 않은 빈 장은 그대로 FAIL · 적었는데 내용이 있는 장은 `WARN:allow-blank(내용 있음)` · PNG 에 없는 번호도 WARN 이다(장을 끼우거나 빼서 목록이 어긋났다는 신호).
- 종료코드: **FAIL 또는 미실행이 있으면 1.** 미실행을 0으로 내보내면 `FAIL=0 WARN=0` 만 보고 통과로 읽게 되어, 완료 조건의 "근거 미발견 0"을 기계가 확인할 수 없다.
- `--pptx` 를 주면 **덱 장수와 PNG 장수를 대조**한다. 다르면 일부만 렌더된 것이므로 FAIL. 보고서에 `deck slides` 로 함께 남는다. python-pptx 가 없거나 `.pptx` 를 열 수 없으면 대조를 못 한 것이므로 `미실행(python-pptx 없음)`(또는 그 사유)을 보고서·표준 출력에 남기고 미실행으로 센다.

### 2-3. FAIL 처리
FAIL은 **소스를 고쳐 재생성**한다. PPTX를 손으로 열어 고치지 않는다(다음 생성에서 되돌아간다).
WARN은 판단 후 (a) 고치거나 (b) 의도임을 보고서에 근거와 함께 적는다. **말없이 넘기지 않는다.**

### 3-2. 시각 확인 항목
시트를 보며 아래 여덟 항목을 **함께** 확인한다 — 항목마다 시트를 따로 다시 보지 않고, 한 번 본 시트에서 여덟 가지를 하나씩 차례로 대조한다(훑어보고 한꺼번에 「이상 없음」이라 하면 놓친다). 여덟 항목은 P4 시각 프리셋의 세부다 — 라운드마다 관점 하나 걸기·프리셋과 가변 5 고르기는 `skill:skill_LKS_original_review-chunking` 을 따른다.

1. **제목만 읽기** — 제목만 이어 읽어 논증이 성립하는가. 주제 라벨이 섞여 있지 않은가.
2. **리듬** — 같은 레이아웃이 이어질 때 내용 유형에 맞는 형태인가(같은 레이아웃이 이어지는 것 자체는 결함이 아니다). 내용 유형에 맞는 형태를 쓰는가. (카탈로그·레퍼런스형 덱에서는 이 항목을 뒤집어, 동종 시리즈 안에서 한 장만 다른 포맷으로 이탈한 페이지를 결함으로 잡는다. → `catalog_deck_rules.md` §8)
3. **여백** — 슬라이드 하단이 비어 있는 정도가 들쭉날쭉하지 않은가. 정렬 기준선이 슬라이드마다 흔들리지 않는가.
4. **밀도** — 한 슬라이드가 두 가지 일을 하고 있지 않은가.
5. **가독** — 축소된 시트에서 제목이 읽히는가(읽히지 않으면 실제 발표에서도 안 읽힌다).
6. **색** — 강조색이 의미 없이 남발되지 않는가. 어두운 배경 슬라이드가 밝은 배경용 글자색을 쓰고 있지 않은가.
7. **4요소** — 구성물 소개 슬라이드에 존재 이유·작동 방식·사용 효과·트리거가 모두 있는가.
8. **넘침** — 글자가 상자를 벗어나거나 잘려 보이지 않는가. 게이트 1의 넘침 검사는 추정이라 경계선 근처를 놓치므로, **여기서 확정한다**.

### 3-3. 전수 확인
**대조 시트는 훑기용이다.** 최종 판정은 개별 PNG를 원본 크기로 열어 확인한다.
- **전 슬라이드를 확인하기 전에 완료를 선언하지 않는다.** 첫 장·마지막 장·눈에 띄는 몇 장만 보고 "전체 확인"이라고 적지 않는다.
- 보고서에 **실제로 연 슬라이드 번호 범위**를 적는다.
- 분량이 많으면 구간(창)을 나눠 **한 검수 서브가 창을 차례로** 열고 창마다 연 슬라이드 번호·지적을 적는다(창마다 서브를 따로 띄우지 않는다 · 창들을 다 봐야 그 라운드 하나 · 이후 라운드는 같은 검수 서브가 필요한 곳만 다시 본다 · 창 규율 = `memory:feedback_review_chunk_discipline`). 이때 그 검수 서브에 대상 파일(PNG·소스) 범위·그 라운드의 관점 하나(P4 시각 프리셋 관점 · §3-2 여덟 항목은 그 라운드에서 함께 본다)·"중대·중간이 0 이면 읽은 범위와 반증 시도를 함께 보고(빈 통과 금지)"를 명시한다. 검수 라운드·관점·청크는 `skill:skill_LKS_original_review-chunking`를 따른다.

### 3-4. 반복
1회 검수로 끝내지 않는다. **매 라운드 청크 스킴을 바꾼다**(전체 훑기 → 섹션별 → 슬라이드별 → 요소 유형별). 같은 방식으로 반복하면 같은 곳을 계속 놓친다.
10라운드를 다 보기 전에는 소스를 고치지 않는다 — 라운드는 발견만 모으고, **10라운드를 다 본 뒤 한 번에 고친 다음** 고친 소스로 게이트1·2를 다시 통과시키고(고치는 과정에서 좌표가 어긋나거나 새 넘침이 생긴다) 재검증한다(같은 검수 서브가 바뀐 단위[고친 소스의 바뀐 슬라이드·다시 렌더한 그 PNG]와 영향 지도 단위를 전문으로 한 번 대조 · 800줄 미만 소스는 파일 전문 · 고침은 이번 검증에 붙은 작업 서브 하나).
종료 기준: **관점 10개 = 검증 1회 = 10라운드 · 조기 종료 없음(10라운드를 다 본다) · 다 본 뒤 한 번에 고침 → 재검증.** → `skill:skill_LKS_original_review-chunking` · 이 10라운드는 A1·A2 본격 덱의 ③ 구조 변경 검증이다(① 치환·② 국소 변경·④ 기계적 변경은 갈래별 검수 · 어느 갈래든 범위 = 바뀐 슬라이드 + 영향 지도 단위 — 판정 원본 = `memory:feedback_chunked_review` 「검수 구분」) — A3·A4(정형·단순 수정) 덱 수정은 자체검수 1회(등급 연동 원본 = 헌법 §3).

## 산출물

**이 목록이 산출물 정의다.** `pptx.md`는 여기를 가리킨다. 파일 7개 + `render/` 하위 3종이며, 하나라도 없으면 미완이다.

```
out/
├── deck.js              소스 (진실의 출처)
├── deck.pptx            생성물
├── source_coverage.md   1단계 — 원본 정독 범위·추출 사실
├── deck_brief.md        2단계 — 청중·목적·결론·청중이 아는 용어 목록
├── slide_outline.md     3단계 — action title 목록 + 제목만 읽기 판정
├── qa_report.md         게이트 2 기계 판정
├── visual_review.md     게이트 3 — 확인 범위·라운드별 지적·수정 여부
└── render/              (클라우드 경로 = 렌더마다 render/<시각>/ 아래 같은 구조)
    ├── png/slide-NNN.png
    ├── montage.png       (13장 이상이면 montage-NN.png)
    └── deck.pdf          (PDF 배포가 필요할 때. `-NoPdf`로 생략했다면 그 사실을 `visual_review.md`에 적는다)
```

### `visual_review.md`에 반드시 적을 것
- 라운드 번호와 그 라운드의 **청크 스킴**
- **실제로 연 슬라이드 번호**(범위가 아니라 목록이 정확하다)
- 지적 사항: 슬라이드 번호 · 항목(§3-2)·관점 · 내용 · 등급(중대·중간·경미) · 조치(수정/의도적 유지 + 이유)
- 종료 판정: 그 갈래의 검수(③ = 10라운드 · 관점 10개 · ①·②·④ = 갈래별 한 번)를 다 봤는지 · 조기 종료 없음 · 남은 중대·중간 결함과 추세
