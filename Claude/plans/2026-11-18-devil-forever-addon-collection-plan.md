**실행 중 새 사용자 지시가 들어오면**: 요청 대장에 다음 R 번호로 적고, 그 지시가 다루는 기능의 Phase 에 넣는다 — 아직 시작하지 않은 Phase 면 그 Phase 의 세부 계획서에, 이미 끝난 Phase 면 Phase 23 의 정정 목록에, 특정 기능이 아닌 일하는 방식에 관한 지시면 「늘 지킬 제약」 표에 넣는다. 범위나 순서가 바뀌면 다음 Phase 를 시작하기 전에 이 문서의 Correction History 에 한 줄 남긴다.

**예상 시간 합계**: Step 6–61 의 고정 부분은 3,930–6,585분(약 66–110시간)이다. 그중 선택 기능 Phase 12–19 가 870–1,425분이며, D7 에서 이 Phase 들을 빼면 3,060–5,160분이 된다. 여기에 Forever 직업 하나당 45–85분(행동단축바 10–15 + unit·자원 15–30 + Hekili 20–40)과, 질감 개선이 필요할 때 60–120분이 더해진다. 받은 Hekili 묶음에 직업 모듈이 9개 들어 있으므로 직업이 9개라면 405–765분이 늘어난다(직업 수는 Step 11 에서 확인한다). D7 에서 기본 제외 기능 두 개를 더 고르면 180–285분이 늘어난다. 사용자가 PC 에서 확인해 주는 대기 시간은 넣지 않았다.

## Summary

**목표**: WoW Forever(클라이언트 폴더 `_forever_`, Codex 가 관찰한 판 1.60.1.70938, koKR) 에서 쓰는 **애드온 모음집**을 만든다. 하나의 큰 애드온이 아니다(R60). 외관에 필요한 것은 하나의 필수 묶음으로 둘 수 있지만, 기능은 각각 따로 켜고 끌 수 있는 별도 AddOn 이다(R44). 모든 직업이 같이 쓰는 공용 모음집이며(R61), 직업별 기능은 Hekili 를 기반으로 한다(R62). 상태 알림과 재사용 대기시간(cooldown, CD)은 한 애드온이 맡는다(R44). 설정 저장·복원과 사용자의 UI 편집은 필수다(R44). 어떤 기능을 넣을지는 통합 UI 애드온들이 갖춘 기능을 조사해 다시 짰다(R77 — Phase Range 의 기능 표).

**시각 기준**: 인벤 자료실 idx45 의 네 번째 샘플 그림(R34)이 기준이고, idx11218 은 오른쪽 미터기 자리를 세 번째 대화창으로 바꾼 모습으로 참고한다(R32·R33). 반투명 배경의 대화창 3개(R23), 제목바·왼쪽 버튼·튀어나온 입력창 없는 깔끔한 채팅(R24), 4K 화면에서 버튼 크기 → 줄과 간격 → 아래부터 쌓은 높이 순서로 정하고 화면 비율로 환산하지 않는다(R21·R22). 2022 FanFix 기준은 철회됐다(R25).

**일하는 순서**(R63·R64·R55): 공통 외관을 첫 구현 Phase 로 만든다 → 기능마다 시작 애드온 하나를 배정해 그 애드온을 최신판으로 맞추고 고치는 것부터 한다 → 고쳐서 안 되는 부분만 새로 개발한다 → 모음집 전체를 함께 검사한다 → 마지막에 완성 목업을 이 채팅에 보여 준다(R46).

**이 환경의 한계와 대응**: 이 세션은 원격 Linux 컨테이너라 게임을 실행할 수 없고 CurseForge 에도 접속하지 못한다. 그래서 (1) 시작 애드온과 참고 애드온의 원본 ZIP 71개는 사용자가 Codex 로 받아 저장소 `References/` 에 올렸고(R75·R80·R81), 새 조사가 필요하면 Codex 에 맡긴다(R80 — Decisions Required D8), (2) 컨테이너에서는 정적 분석·Lua 문법 검사·오프라인 로드 harness·렌더 목업까지 검증하며, (3) 게임 안에서만 확인되는 로드 오류·전투·taint(보호된 UI 를 애드온 코드가 건드려 전투 중 동작이 막히는 현상)·저장은 Phase 마다 짧은 확인 목록으로 묶어 사용자가 퇴근 후 PC 에서 한 번에 돌린다(A1 제안).

### 기능 범위가 넓어진 경위

R1 의 첫 요청은 단축키·체력/마나·미니맵이었고 「부가 기능 제외」 였다(Codex 대장 `REQUEST_LEDGER.md:5` 의 요지 — 첫 메시지 원문은 저장소에 없다). 그 뒤 사용자가 범위를 넓혔다: R44 「기능적인건 전부 따로 선택할수 있어야지. 그리고 설정 저장 복원도 당연히 필요하고 ui를 유저가 수정 가능하게 커스터마이징도 열어 줘야하고」, R45 「이벤트 얼럿같은 것은 기존것을 그냥 적용해도 되잖아? 데미지 미터기 어그로미터기 같은것도」, R60 「애드온 모음집이 목표」, R61 「직업별 전부로하자 공용 애드온으로」, R77 「보통의 통합 애드온 ui들에서 갖추고 있는 기능들을 조사해서 우리가 어떤기능을 포함해야하는지도 다시 얼개를 짜고」. 그래서 원래 13개 기능은 사용자 원문으로 정해진 **필수 기능**으로 두고, R77 조사에서 나온 기능은 **선택 기능**(사용자가 D7 에서 만들지 고름)과 **제외**로 나눴다. R1 의 「부가 기능 제외」 는 경매·우편 같은 편의 기능에는 아직 유효하다고 보고(A1 판단) 그 기능들은 기본값을 제외로 두었다.

**Codex 후보에서 바꾼 곳과 이유 (A1 제안)**

1. **질감 개선(R52)을 대안 테마 Phase 에서 공통 외관 Phase(Step 14)로 옮겼다.** 데빌 기본 테마의 질감은 공통 외관 자체이므로 처음 만들 때 판정해야, 뒤의 기능 Phase 스킨이 고친 자산을 그대로 쓴다.
2. **저장·복원과 사용자 편집을 다른 기능 Phase 뒤(20·21)로 옮겼다.** 두 기능은 다른 모든 애드온의 설정을 다룬다. 다른 애드온이 생긴 뒤에 만들어야 다시 고칠 일이 줄어든다. 대신 Phase 2 에서 등록 규약(Implementation Interfaces)을 먼저 정해 각 기능 Phase 가 자기 설정을 등록해 둔다.
3. **대화창을 미니맵보다 앞(Phase 4)에 두었다.** R24 에서 가장 강하게 지적된 부분이다.
4. **대안 테마(R51 「제시해줄래」)는 관리 기능 뒤(Phase 22)에 구현까지 하고, 보여 주는 것은 최종 목업(Phase 24)에서 한다.** 디자인 판단이 위임돼 있어(R50·R53) 테마 구현은 「작업할 수 있는 것」 이고, R55 에 따라 목업은 그 뒤다. 컨셉 후보 「네온 보컬 스테이지」·「백자와 먹빛」 은 Codex 기록의 제안이며 사용자 선택이 아니다. Step 54 에서 다시 판단한다.
5. **R77 조사로 선택 기능 Phase 8개(12–19)를 새로 넣었다.** 기본값 규칙: 통합 UI 8개 중 5개 이상이 갖춘 기능이거나 V42 가 이미 담고 있던 기능(R47)은 만든다, 그 밖은 만들지 않는다. 예외로 편의 자동화는 V42 에 있지만 R1 때문에 제외를 기본값으로 했다.
6. **저장·복원 시작 애드온을 Reflux 에서 ProfileManager 로 바꿨다.** ProfileManager 는 Forever 판이 확인됐고(survey.md:91) 지원 애드온별로 골라서 적용하는 흐름이 범위 복원 요구와 가장 가깝다. Reflux 정식판은 Forever 판이 확인되지 않았고(TOC 60000) V42 판은 전역 전환 문제가 있다(Codex 기록). ProfileManager 가 우리 애드온들을 얼마나 지원하는지는 아직 모른다 — Step 50 에서 `Providers.lua`·`Addons.lua` 를 읽고 모자라면 Reflux 의 기전을 참고해 그 부분만 만든다.
7. **원천 확보 단계를 「수령 완료 → 해제·manifest·정적 분석」 으로 바꿨다(R81).** 원천 대기 때 쓰던 대체 시작점 열과 긴 미루기 규칙은 아래 짧은 예외 규칙으로 줄였다.

### 원천이 모자랄 때 (남은 예외)

시작 애드온 ZIP 은 모두 받았다. 그래도 어떤 Phase 가 저장소에 없는 파일(예: 더 새 판, 비교용 원천)이 꼭 필요하다고 판단되면 그 Phase 를 「원천 대기」 로 두고 다음 Phase 를 먼저 한다. 필요한 파일은 D8 형식의 Codex 조사 요청으로 최종 보고에 적어 사용자에게 넘긴다. 파일이 들어오면 지금 하던 Phase 가 끝난 직후 그 Phase 로 돌아간다. 순서를 바꿀 때마다 진행 표와 Phase N 표의 상태 칸에 적는다.

- 사용자 PC 를 원격으로 조작하거나 게임에 직접 설치하는 것(설치는 사용자가 확인 목록대로 한다).
- 매크로 이동·변환·키 자동 배정 (R17), 제외 표에 둔 기능과 경매 같은 요청하지 않은 부가 기능 (R1·R4).
- 원본 ZIP·`References/`·Codex 기록·Step 5 설계 파일 수정·정리 삭제. 이 컨테이너의 네트워크 허용 재요청(R78·R79).

## Implementation Changes

### 모음집 구성 (A1 제안)

- **필수 묶음**: 공통 외관(`DevilForever_Core` — 패널·구분선·장식·글꼴·테마 토큰·등록 규약), Masque 와 Onyx 스킨, 설정 저장·복원(Phase 20), 사용자 UI 편집(Phase 21). R44 의 「외관을 위한 애드온들 가져다쓴것들 필수 적인건 하나로 묶더라도」 와 「설정 저장 복원도 당연히 필요」 를 묶음 단위로 옮긴 것이다. 폴더는 각자 따로 두고 manifest 에서 필수로 표시한다.
- **개별 기능 애드온**: Phase 3–19 의 기능. 각자 자기 폴더·TOC·저장 변수를 갖고, 꺼져 있으면 그 기능의 스킨 연결 코드도 로드되지 않는다(스킨 연결은 해당 애드온을 의존으로 둔 별도 폴더 `DevilForever_Skin_<애드온>` 으로 둔다).
- **이름**: 우리가 새로 만드는 폴더는 `DevilForever_` 로 시작한다. 고친 시작 애드온은 원래 폴더 이름을 유지하고 manifest 에 「고침」 으로 표시한다(원래 이름이어야 다른 애드온의 의존이 깨지지 않는다). 사용자 관례가 따로 있으면 그것을 따른다.

### 시작 애드온을 고치는 방식 (A1 제안)

R63 의 「수정 및 최신화」 를 다음 순서로 한다.

1. **최신화**: 받은 최신 Forever 판을 기준으로 삼는다. 저장소 안 옛 판(V42 동봉본 등)과 다르면 차이를 기록하고 최신판을 쓴다. V42 의 profile 은 설정값 참고로만 쓴다.
2. **설정으로 해결**: profile·옵션 값으로 되는 것은 설정으로 한다. 기본 설정은 우리 애드온이 처음 로드될 때 한 번 넣어 주고, 사용자가 바꾼 값은 덮어쓰지 않는다.
3. **스킨 연결로 해결**: 원본을 건드리지 않고 그 애드온이 공개한 스킨·테마 API 나 Masque 로 외관을 맞춘다.
4. **원본 수정(fork)**: 1–3 으로 안 될 때만, 라이선스가 허락하는 제품만(D4) 한다. 원본 폴더를 고치므로 CurseForge 앱 자동 업데이트가 덮어쓴다 — 확인 목록에 그 애드온의 자동 업데이트를 끄라는 항목을 넣고, manifest 에 원본 판을 고정한다.
5. **새로 개발**: 그 기능이 요구를 끝내 못 채우는 부분만, 무엇이 왜 안 되는지 적은 뒤 그 부분만 만든다. 우리 구현이 더 나으면 유지하고 아니면 원래 것을 쓴다(R48).

### 기능 Phase 의 공통 단계

모든 기능 Phase 는 같은 두 단계를 밟는다. 아래에 한 번만 적고 각 Phase 세부 계획서가 이를 따른다.

- **앞 Step (읽기·설계)**: `Collection/upstream/` 해제본에서 시작 애드온의 TOC·로드 순서·저장 변수·관련 Lua 를 전문 정독 → 비교 대상은 필요한 부분만 읽는다 → 요구(「늘 지킬 제약」, Step 5 설계, 위 기능 표의 「이 Phase 가 하는 일」)와 현재 동작을 대조 → 「통째 사용 / 기능만 가져옴 / 고침 / 새로 개발」 을 기능 단위로 판정(R49) → 바꿀 파일·설정과 등록할 항목을 적은 설계.
- **뒤 Step (수정·검증·확인 목록)**: 설계대로 고친다 → 컨테이너 검증(문법·정적 검사·harness 로드·필요하면 렌더) → 그 Phase 의 사용자 PC 확인 목록 작성 → manifest·patch 갱신 → 설치용 ZIP 다시 빌드.
- 새로 개발할 부분이 커서 Step 하나를 더 써야 하면 뒤 번호를 밀지 않고 그 Phase 안에 하위 번호(예: Step 22a)로 붙인다.

### 기능이 아닌 Phase

- **Phase 1 준비**: Step 8 은 `References/` 의 ZIP 을 읽기 전용으로 두고, 시작 애드온과 비교 대상 ZIP 을 스크립트로 `Collection/upstream/` 에 푼다(경로 검사·링크 차단·SHA256 대조). 풀면서 TOC·의존·저장 변수·라이브러리 판·라이선스 파일을 기계로 뽑아 manifest 초안을 만든다. Step 9 는 `Collection/` 자리와 `.gitignore` 한 줄(해제본 제외), `lupa` 설치, 묶음 빌드 스크립트. Step 10 은 가짜 게임 API 위에서 TOC 순서대로 Lua 를 읽어 보는 harness 이며 V42 애드온으로 먼저 시험한다. Step 11 은 Hekili 직업 모듈·FUF 원천으로 직업·특성·자원 표를 만든다.
- **Phase 23 연계**: 필수 묶음만 켠 상태, 전부 켠 상태, 개별 기능을 하나씩 뺀 상태에서 harness 로드와 등록 목록을 검사하고, 발견한 결함을 고친다.
- **Phase 24 최종 목업**: 4K 전체 화면, 하단 원배율 잘라 보기, 단축키 글자 확대, 직업별 자원 표시 예시, 데빌 기본 테마와 대안 테마 비교를 렌더한다. 모든 그림에 「목업 — 실제 게임 화면 아님」 을 표시한다. 렌더는 실제 자산·글꼴과 Step 5 좌표로 Python 에서 그린다.
- **Phase 25 고정**: 사용자 PC 확인 결과에서 나온 결함을 고치고, 최종 묶음 ZIP·manifest·복원 방법·남은 미검증 목록을 고정한다.

- 각 기능 Phase 의 뒤 Step 이 그 Phase 의 확인 목록(`Collection/checklists/phase<ID>.md`)을 만든다. 항목은 10개 이하이고, 항목마다 「하는 법 · 기대 결과 · 결과 한 줄 양식」 을 적는다.

## Decisions Required

이미 정해진 것(모음집·전 직업·Hekili 기반·공통 외관 먼저·기능마다 Phase·시작 애드온 수정 먼저·목업 마지막·시각 기준·원천은 사용자가 올린 ZIP)은 다시 묻지 않는다. 아래는 사용자만 정할 수 있는 열린 질문이다. 답이 없으면 기본값으로 진행하고 기록한다.

**D1 — 사용자 PC 확인을 언제, 얼마나 할지**
- 내용: 게임 안 확인은 사용자 PC 에서만 된다. Phase 마다 확인 목록이 나온다. 오류를 모아 보려면 오류 수집 애드온(BugSack + BugGrabber, 둘 다 Forever 판 확인 · V42 에도 동봉)을 확인용으로 함께 설치하는 것이 좋다.
- 근거: R46(출근 중 인게임 확인 불가), 이 컨테이너는 게임 실행 불가.
- 선택지: (가) 작업한 날마다 그날 끝난 Phase 목록을 한 묶음으로 받아 퇴근 후 확인 / (나) 중간에는 확인하지 않고 Phase 23 뒤 전체 묶음으로 한 번만 확인 / (다) 기능 Phase 하나 끝날 때마다 바로. 오류 수집 도구: (ㄱ) 함께 설치 / (ㄴ) 설치하지 않고 게임 기본 오류 표시만.
- 기본값: (가)·(ㄱ). 결과를 기다리느라 작업을 멈추지 않는다.

**D2 — Hekili 표시 범위**
- 내용: Hekili 는 상태·proc 알림과 다음 행동 추천을 모두 보여 줄 수 있다.
- 근거: R6(「이벤트 얼럿을 품은 애드온」), R44(상태+CD 한 애드온).
- 선택지: (가) 알림과 추천 둘 다 표시, 각각 끌 수 있게 / (나) 알림과 CD 만 / (다) 추천만.
- 기본값: (가) — R6 의 기억에 가장 가깝다.

**D3 — 대화창 3개의 역할(채널 분담)**
